# スパイラルの定義と進行

進め方の決定: DEC-024。この文書が、進め方の定義と進行の記録の正本。

## 1. スパイラルの定義

設計はスパイラルで進める。設計の柔軟性は、設計をその場で継ぎ足すこと(パッチ)ではなく、**新しいスパイラルとして回すこと**で確保する。

1 つのスパイラルは、次の 6 つから成る。

1. **目的と制約の確認**: このスパイラルで何を決めるか。前提(決定ログ)は何か。
2. **前提の検査(preflight)**: 設計が頼りにしている環境の前提を、実測して確認する(§2)。
3. **リスクの特定と、先に検証するもの**: 設計の前提のうち、外れると手戻りが大きいものを選び、設計の前に検証する(実験、spike)。
4. **設計とテスト仕様**: 設計書と、対のテスト仕様を同時に作る(L1 ↔ E2E、L2 ↔ 結合、L3 ↔ 単体)。
5. **レビュー**: 設計書を起草した時点で、DeepSeek(`deepseek-v4-pro`)のレビューを**最大 2 回**入れる(DEC-030)。指摘は [reviews/](reviews/) に残し、作成者が本文と突き合わせて確認できたものだけを反映する。2 回で致命が残る場合は、3 回目に進まず、概念を見直す。
6. **決定**: オーナーの判断が必要な点は、「事実 → 最小の問い → 答え」に分けて聞く。決定は [decisions.md](decisions.md) に記録する。

パッチにしないための規則:
- 指摘が出たら、**規則を足して塞ぐ前に、概念を疑う**。同種の指摘が再発したら、足すのをやめて、構成を見直す(第4版の教訓。[reviews/L1_review3_2026-10-27.md](reviews/L1_review3_2026-10-27.md))。
- 承認済みの設計を変えるときは、設計書を直し、レビューを受け、承認を更新する(新しいスパイラル)。コードや設定だけを先に変えない。
- 収束の目安: 致命が 0 件。同種の問題が形を変えて再発していない。
- 選択肢が複数出る問いは、問いが大きい。分解してから聞く。

## 2. 前提の検査(preflight)

各スパイラルの最初に実行する。設計の規則に現れない、環境の前提を確かめる。**結果は日付と証拠を添えて記録する。「通った」と報告する前に、自動の経路が実際に動いた証拠を見る。** 手動で実行したものは、手動と書く。

|---|---|---|
| 品質ゲートの入口が 1 つで、実行可能 | `ls -l scripts/gate.sh`、`git ls-files -s scripts/gate.sh` が 100755 | 解消。以前は `verify_all.sh` で、全体設定が呼ぶ `gate.sh` が存在しなかった |

| git のフックが導入されている | `ls .git/hooks`、`gov doctor` | 未導入 |

定義: 二重管理とは、**同じ情報が手作業で 2 か所以上に維持され、食い違いうる**こと。1 つの定義から派生した実装(例: ルールの定義 1 つに対する、フックと ruleset の 2 つの実装)は、定義が 1 つなら二重管理ではない。ただし、実装の数は最小にする(#16)。

## 5. スパイラル 2(L2)の計画

**目的**: L1 の規則を、実装できる契約(型、インターフェース、アルゴリズム、フックのプロトコル、コマンド、エラーの扱い)に落とす。設計書は `03_architecture.md`、対のテスト仕様は `03_integration_tests.md`。

**範囲**: `Repo` と `Change` の型、`Approval` と `Finding` のモデル、K・D・T・Q のアルゴリズム、`gov` のコマンドと終了コード、フックのプロトコル(入力と出力、終了コード、メッセージ)、GitHub Action の入口、エラーの扱い(D4)、ハッシュの正規化(D3)、品質ゲートの正本の統一(監査 #15)、`main` への直接コミット禁止の実装(監査 #16)、テスト構造(D10)。

| R1 | `main` 側のチェッカーで CI を実行する方式が成立するか(`pull_request_target`) | `main` にワークフローを置く PR を出して実測(外向きの操作を伴う) | 大(A3 の対策の核) |
