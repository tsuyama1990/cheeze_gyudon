## 2. 考え方(3 つに分ける)

第4版までの失敗は、性質の違う 3 つを 1 つの仕組みに混ぜたこと。 [推論: L1_review3 §4]

| 性質 | 内容 | 仕組み |
|---|---|---|
| **品質検査(Q)** | どの PR にも常にかける検査: lint、型、テストの合格、カバレッジ、タグの整合 | CI。ゲートの条件を持たせない |
| **鍵(K)** | 人間が承認した設計がなければ、新しい挙動を入れられない。新しい挙動は、テストまたは仕様の変更を伴う `src/` の変更で表れる | 承認マニフェストのハッシュ。「`src/**` を変え、かつテストまたは仕様も変える」PR にだけ適用 |
| **指針** | ペアを揃える、ゲートの順序、レビューの観点 | テンプレート、規約、フックの通知。CI の必須条件にしない |

ゲートの順序とペアの有無は、承認のとき(決定 PR)に 1 度だけ確認する(§5)。PR ごとには確認しない。設計もテストも、途中の状態を経て作られるので、途中の状態を拒否する構造にしない。

## 3. 構成要素

```
 adapters:  cli (click) │ claude_hook (stdin JSON) │ github_action (PR 差分)
                │ 呼ぶ
            checks  (検査。Findings を返す)
                │ 使う
            derive  (承認の有効判定、現在ゲートの表示用の計算。検査は呼ばない)
                │ 使う
            domain  (型・ID・ゲート列・成果物パターン)
```

依存の向きは `adapters → checks → derive → domain` の一方向。逆向きの import を禁止する。 [推論]

| 構成要素 | 責務 | 副作用 |
|---|---|---|
| **domain** | Requirement / Gate / Deliverable / Approval の型。ID 形式(`REQ-YYYY-NNN`、機能タグ `REQ-YYYY-NNN-Fnn`)。ゲート列。成果物パターン | なし |
| **derive** | 承認が有効か、現在ゲート(表示用)を計算する(§5) | `Repo` 経由で読むだけ |
| **checks** | K、D、T と、Q のうちタグの整合を検査し、Findings を返す | `Repo` 経由で読むだけ |
| **adapters/cli** | `gov` のコマンド。導出と検査の結果を表示する | なし |
| **adapters/claude_hook** | Claude Code のフック(§6)。stdin の JSON を受け、`checks` を呼び、拒否は exit 2、通知は標準出力 | なし(Stop の失敗回数のみ保存、§6) |
| **adapters/github_action** | PR の `base` と `head` から `Repo` を作り、`checks` を呼び、必須チェックの結果を返す | なし |

### 3.1 `Repo`(`derive` と `checks` が使う唯一の入口)
`derive` と `checks` は、ファイルシステム、時刻、環境変数、git を直接使わない。次の薄いインターフェースだけを通して読む。 [決定: RepoView を薄いインターフェースに替える(2026-10-27)]

| 操作 | 内容 |
|---|---|
| `read(path, ref)` | `ref` の時点のファイルの内容。なければ None |
| `list(ref)` | `ref` の時点の追跡ファイルのパス一覧 |
| `changes(base, head)` | 変更の一覧。改名は旧パスと新パスの両方を持つ |

- `ref` は `base`(`main`)、`head`(PR の先頭。push のフックでは HEAD)、`worktree`(作業ツリー。書き込みごと、commit、Stop のフック)の 3 つ。
- `index` は使わない。`git add … && git commit` のように、`PreToolUse` の時点では `git add` がまだ走っておらず、`-a` も同じで、index を正しく検査できない。また Q(pytest、mypy、diff-cover)は作業ツリーを読む。commit のフックは作業ツリー全体を検査する(未ステージの変更も含むため、偽陽性がありうる)。 [Opus X3 への対応]
- 実装は adapters が持つ(git、作業ツリー、テスト用の偽物)。`derive` と `checks` は実装を知らない。これで、フックと CI が同じ `checks` を呼べ、単体テストは偽物で書ける。
- フックは `base` を `origin/main` とし、必要なら `git fetch` する。ネットワーク禁止の制約は撤廃した。 [決定: 2026-10-27]

## 4. 規則

### 4.1 機械的に判定する規則(CI の必須チェック)

| ID | 適用対象 | 規則 |
|---|---|---|
| **K** | `src/**` を変更し、かつ `tests/**` または `.specs/**` も変更する PR | (a) `base` に、有効な承認が**ちょうど 1 つ**ある。0 個、または 2 個以上なら失敗 (b) この PR は、`approval.json` と、マニフェストが列挙する承認済みファイル(01〜05)を変更しない (c) この PR が変更するテストの marker の要件と、変更する `.specs/<REQ>/` の要件は、すべて (a) の要件である |
| **D** | `approval.json` を変更または削除する PR(決定 PR) | 状態 `open`: (a) `head` でゲート 1〜4 の成果物(設計と、対のテスト仕様の**文書**)がそろっている。ゲート 4 の対は文書(例: `04_test_spec.md`)で、実行可能なテスト(`tests/`)ではない (b) ハッシュが `head` の内容と一致し、承認済みファイルの集合が `head` の `.specs/<REQ>/0[1-5]_*` と一致する (d) 変更後、`open` の承認が 2 つ以上にならない。状態 `closed`: (c) 仕様の全機能タグに対応するテストの marker が存在する。状態 `withdrawn`: 追加の条件なし(未完の要件の取り下げ)。(a)(b) は `closed`・`withdrawn` には求めない(履歴として閉じる要件を含む)。`approval.json` の削除は失敗 |
| **T** | すべての PR | (a) テスト関数は、形式が `REQ-YYYY-NNN-Fnn` の `requirement` marker を持つ (b) marker の要件の仕様(`.specs/<REQ>/01_req_spec.md`)が存在し、そのタグに含まれる (c) テストのファイル(`test_*.py`、`*_test.py`)は `tests/**` にある |
| **Q** | すべての PR | lint(ruff)、型(mypy)、デッドコード(vulture)、テストの合格、分岐カバレッジが `pyproject.toml` の設定値以上、`src/**` の**変更行のカバレッジ**が設定値以上(`diff-cover`、dev 依存に既にある。閾値は設定に置き、`--fail-under` を必ず指定する。テストコードは対象外)。新しい `# pragma: no cover` の追加は失敗。`closed` にする決定 PR(D(c))も、この Q を通る |

- **承認が有効** = マニフェストが存在し、状態が `open` で、承認済みファイルのハッシュが `base` の現在の内容と一致し、承認済みの集合が `base` の `.specs/<REQ>/0[1-5]_*` と一致する(承認後に足したファイルがあると無効)。
- 仕様のタグにテストがない状態(途中)は、`open` の間は許す。そろっているかは、`closed` にする決定 PR のときだけ確認する(D(c))。 [決定: G3 の限定(2026-10-27)]
- 規則どうしの適用条件は上の表のとおりで、種別と順位による合成はない。 [決定: 述語化(2026-10-27)]
- **同時に open な承認は 1 つ**とする。 [決定: 2026-10-27。根拠: 並行開発が統合の混乱を生んだ。1 から複数への緩和は後から追加でき、複数から 1 へは戻せない]。K の (c) は、関連要件の推定ではなく、変更が open の要件の外に出ていないことの**照合**である。複数要件の並行は MVP 後に設計する(D9)。
- K の (b) により、設計を直す PR と、それを使う実装 PR は分かれる。承認済みファイルを直す PR は、K の対象にならず(`src/` を変えない)、直した後に決定 PR で承認を更新する。 [Opus X1、DeepSeek V7-02 への対応]

| ID | 規約 |

## 5. 承認と導出

### 5.1 承認マニフェスト
`.specs/<REQ>/approval.json`(名前は L2 で決める)。中身は、要件 ID、状態(`open` / `closed` / `withdrawn`)、承認した `01〜05` のうち存在する各ファイルの SHA-256。書く主体は人間(C1)。 [決定: 承認マニフェストの採用(2026-10-27)]

- テスト本体は承認の対象にしない。AGENT.md の「テストの期待値を弱めない」は規約として残る。承認後のテストの弱体化を機械検出するのは MVP 後。 [決定: N5 の取り消し(2026-10-27)]
- 巻き戻しは、承認済みファイルの変更(ハッシュ不一致で承認が失効する)、またはマニフェストの更新で表す。ESC 記録は作らない。理由は PR の説明とコミットメッセージに残す。
- 完了は、状態を `closed` にする(決定 PR)。取り下げは `withdrawn`(未完の要件を、`closed` の条件 D(c) なしで閉じる)。いずれも、その要件の承認は無効になり、テストまたは仕様も変える `src/` の変更は K(a) で失敗する。再び開くには、人間が `open` に戻す決定 PR を出す(他に `open` があれば、先にそれを `closed` か `withdrawn` にする)。 [Opus X5 への対応]

### 5.2 保存しない状態
現在ゲート、status は保存しない。`.specs/state.json` は廃止する。現在ゲートは**表示用**に、`base` の内容から「ペアがそろっていない最小のゲート」として計算する。CI の必須条件には使わない。 [決定: D2]

### 5.3 K の適用と、小さな変更
承認が防ぎたいのは、承認されていない**新しい挙動**が入ること。新しい挙動は、テストまたは仕様の変更として表れる。 [決定: 2026-10-27]

| PR の内容 | K | 理由 |
|---|---|---|
| `src/**` と、`tests/**` または `.specs/**` を変える | 適用 | 新しい挙動の可能性がある |
| `src/**` だけを変える(テストも仕様も変えない) | 適用しない。Q は必須 | リファクタに使える。**既存テストが検出する挙動は変わらない**。検出しない挙動の変更は防げない(下) |
| 新しい行を足したが、テストで覆われていない | Q の変更行のカバレッジで失敗 | テストなしで挙動を足す抜け道を塞ぐ |
| バグ修正(回帰テストを足す) | 適用 | open の要件の下で行う(回帰テストの marker はその要件)。その要件が `closed` なら、人間が `open` に戻す(他に `open` があれば、先にそれを閉じる) |
| バグ修正をテストなしで(`src/` だけ) | 適用しない | 検出できない(下) |
| `pyproject.toml`、`uv.lock` だけ | 適用しない | `src/**` を含まない。検証機構として人間のマージが必要(§4.4) |

**前提の訂正と決定 (DEC-023)**: 「既存のテストが全部通り、カバレッジを満たせば、`src/` だけの変更で挙動は変わらない」は成り立たない。変異を入れた実験で、覆われた行の挙動を変えても全テストが通り、カバレッジも変わらなかった([reviews/L1_review5_2026-10-27.md](reviews/L1_review5_2026-10-27.md) §3)。変更行のカバレッジも、行が実行されれば満たされる。テストを足すと K がかかり、足さなければかからないため、バグ修正でテストを省く動機も生まれる。これらを**非保証(§4.5)として受け入れる**。意図しない挙動の変更を検出するのは、テストの質(変異テストなど)の役割で、K の役割ではない。 [決定: DEC-023]

## 6. フック(プロジェクトごとの `.claude/settings.json`)

`gov init` が、入れ子形式の設定を出す。フックは `gov hook <イベント>` を呼ぶ。拒否は exit 2 と標準エラー出力のメッセージ。 [データ: proposal §6 U5]

| イベント | やること | 性質 |
|---|---|---|
| `PreToolUse`(Edit / Write / MultiEdit / NotebookEdit) | `src/**` への書き込みで、有効な承認がちょうど 1 つでなければ、通知を出す(「テストまたは仕様も変える場合は、先に承認が必要」)。**拒否しない**。書き込みの時点では、リファクタ(K 不要)か新しい挙動(K 必要)かを区別できないため | 通知 |
| `PreToolUse`(Bash の `git commit*`) | 作業ツリー全体(`worktree`)に対して、K、D、T、Q を実行する。K はここで初めて、テストや仕様の変更が伴うかを判定できる。未ステージの変更も検査対象になる | 拒否 |
| `PreToolUse`(Bash の `git push*`) | HEAD(`head`)に対して、K、D、T を実行する(push されるのは HEAD) | 拒否 |
| `Stop` | 全検査を実行する。通らなければ終了させない(exit 2)。連続 3 回失敗したら、終了を許し(exit 0)、通らない理由を報告する。失敗回数は、リポジトリ内の未追跡の場所に保存し、成功で消す(場所は L2) | 拒否 |
| `SessionStart`、`UserPromptSubmit` | 状態(現在ゲート、承認の有効/失効、「テストまたは仕様も変える `src/` 変更が可能か」)を、エージェントに伝える | 通知 |

- フックは助言であり、強制ではない(N1)。`git commit` を経ない書き込み(`git stash` など)は検出できない。配線の確認は、`claude -p` で実際に拒否されることを手動で確かめる(LLM の挙動に依存するため、自動のテストにしない)。 [データ: 現行フックは読み込まれず、exit 1 では拒否にならない]
- 速度の要件はない。 [決定: 2026-10-27]

## 7. フロー

1. 人間が要件を出す。エージェントが `.specs/<REQ>/` に 01〜04(設計と、対のテスト仕様)を作り、PR を出す。途中の PR は Q と T だけで通る。
2. 設計が固まったら、決定 PR で `approval.json`(`open`、ハッシュ付き)を入れる。D を CI が確認し、人間がマージする(C1、C2)。
3. 実装 PR(複数可)で `src/` とテストを入れる。K を CI が確認する(承認済みファイルは変えない)。
4. 完了時に、人間が状態を `closed` にする決定 PR を出す。D(c)で、仕様の全タグに対応するテストがあることを確認する。未完のまま閉じるときは `withdrawn`。
5. 設計を直す必要が出たら、`01〜05` を直す PR を出す(承認が失効する。この PR は `src/` を変えない)。決定 PR で承認を更新するまで、テストまたは仕様も変える `src/` の PR は K で失敗する。

## 11. 移行の順序(ブートストラップ)

検査を導入する PR が、自分の導入する K にかかる問題を避けるため、必須チェックにするのを**最後**にする。

1. `Repo`、`derive`、`checks` を、CI の必須にしないまま実装する(`pull_request` では実行するが、結果は参考)。
2. 現行テストの marker を整理する。**タグの付け替えだけを行い、テストを削除しない。** 対象の件数(marker なし、形式不正、仕様なし)と、削除した場合のカバレッジの実測は [reviews/L1_review5_2026-10-27.md](reviews/L1_review5_2026-10-27.md) と [background/as_is_inventory.md](background/as_is_inventory.md) §7。
3. 現行の `REQ-2026-001` は、状態 `closed` のマニフェストを置いて履歴として残す。`closed` には D(a)(b) を求めないので、02〜04 がなくても置ける。D(c) は、仕様の F01〜F05 すべてにテストがあるので通る [データ: F01 17 本、F02 6 本、F03 4 本、F04 7 本、F05 3 本]。**F01・F05 のテスト(廃止する機能のもの)の削除は、この後**に行う(先に消すと D(c) が失敗する)。v2 は新しい要件(例: `REQ-2026-010`)として、01〜04 と `approval.json`(人間が作成)を用意する。
4. フックを入れる(`.claude/settings.json`)。実機の `claude -p` で拒否を確認する。AGENT.md を更新する(ゲート 4 の対、フックの記述)。
5. 保護ルール(§8)を適用し、必須チェックにする。`ci-verify` は `state.json` の廃止と同じ PR で置き換える。以降、直接 push は禁止になり、PR で進める。
