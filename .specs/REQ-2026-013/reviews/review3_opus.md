### 新しい問題
- **N-1 [Major] worked_example §2 手順 1**: 保守した追跡テストに、REQ ごとの手動確認の ID を直書きすると、同じ問題が再発する。feat/global-guard の実装は `MANUAL = {"REQ-2026-010": …, "REQ-2026-011": …}` の形になっている[原典]。この形では、新しい REQ(013 の L1-M20〜22 など)が出るたびに、010-F08 の関数を変えることになり、閉じた後は K.c に当たる。保守の完了条件に、次の 2 つを書くべき。
  - 手動の行は、計画の表から導く(ID の接頭辞や列)。
  - 対象の REQ は、`.specs` と承認から導く。
- **N-2 [Major] 02 §3 の Q2「検証機構の変更」**: `_GLOBS` には `src/jtc_gov/**` と `AGENT.md` が含まれる。文字どおり読むと、cheeze_gyudon の実装の判断がすべて「変更を決める時点」で Q2 になり、止まりすぎる。承認済みの REQ の実装でも、マージの前に gov が人間のマージを出して二重になる。
  - 前倒しする対象を、次のものに限定して列挙すべき: `scripts/**`、`.github/**`、`pyproject.toml`・`uv.lock`(依存)、`.claude/settings.json`・hooks、`conftest.py`。
  - `src/jtc_gov/**` と `AGENT.md` は、承認の範囲内ならマージの時点(C2)だけにする。
- **N-3 [Minor] worked_example §2**: ローカルの main を新しい履歴に置き換える方法が書かれていない。merge-to-main.sh は使えない(`--no-ff` マージのため)。
  - §3.1(不可逆な操作を書かない)に合わせて、先に `backup/main-<日付>` を作る。main 以外のチェックアウトから `git branch -f main <新>` を実行する。push の前に、新しい main で `scripts/gate.sh` を全段走らせる。
  - branch_guard は commit と編集だけを止め、`branch -f` は止めない[原典]。
- **N-4 [Minor] 013 自身の採用の仕方**: 013 には gate のペアが 3 つしかない。`approval.json` を作ると D.a で落ちる[原典 `checks/d.py` の `_check_open`]。
  - 「013 は approval.json を作らない。採用は DEC-058〜063 への 1 問の回答(引用を decisions.md に残す)」と明記すべき。
  - あわせて、010 の C1 の本文は変わらず残る(閉じた設計は編集できない)。R19 に「C1 は DEC-062 で置き換え」と 1 句入れるべき。
- **N-5 [Minor] 02 §4 と C2**: C2(approval.json の PR は人間がマージ)は変えない、としている(01 §2)。それなら、承認の回答が C2 のマージの指示を兼ねることを 1 文書くべき。書かないと、マージの確認がもう 1 回増えるか、C2 が黙って変わる。
- **N-6 [Minor] 01 の冒頭**: 「DEC-058〜062」とあるが、decisions には 063 まである。
