## 2. 机上の PR 試験(2 系統の結果の統合)
新規要件の設計 PR、決定 PR、`closed` にする PR、テストだけ・doc だけ、検証機構、依存更新、リファクタ(覆われた行)は、期待どおり。問題が出たのは次の PR:
- 承認済みの仕様を、`src/` とテストと同時に変更する PR(通ってしまう)。
- 別の要件の仕様・`src/`・テストを、open の要件があるときに入れる PR(通ってしまう)。
- `src/` だけで既存の挙動を変える PR(通ってしまう)。
- open の未完の要件を取り下げる手段がない、open 中にバグ修正のための要件を open にできない。

## 3. 決定 (2) の前提の再確認(オーナーの判断が必要)

**前提と結果**: 決定 (2) の根拠は「`src/` だけの変更で、既存テストが全部通り、カバレッジが 90% あれば、挙動は変わっていない」だった。Opus が、この環境のコードに変異を入れて全テストを実行した結果は次のとおり。

| 変異 | 結果 |
|---|---|
| `tracer.py` の `isinstance(node, (ast.FunctionDef, ast.ClassDef))` を `FunctionDef` だけにする(クラスに付けた marker を無視する) | 95 passed、カバレッジ 95.58% のまま |
| `gate_keeper.py` の `review.status != "APPROVED"` を別の条件にする(未承認のレビューで止まらなくなる) | 95 passed |
| `verifier.py` の拒否メッセージの変更 | 95 passed |
| 小さな模型で、覆われた行の `x*2` → `x*3`、`return 0` → `return 7 if x == -100 else 0` | どちらも `diff-cover` 100%、rc=0。`--branch-coverage` でも同じ |

**帰結**: 覆われた行の挙動を変えても、テストの合否とカバレッジは変わらない。変更行のカバレッジは、行が実行されたかしか見ない。PR を「`src/` だけ」と「テストだけ」に分ければ、K は一度も適用されない。バグ修正は、回帰テストを足すと K がかかり、足さなければかからないため、テストを省く動機が生まれる。

**位置づけ**: K が防ぎたいのは「承認されていない新しい挙動を、意図して入れること」。意図しない挙動の変更(リファクタの失敗)を検出するのは、テストの質(変異テストなど)の役割で、K の役割ではない。ただし、決定 (2) の説明(「ほぼ入れられない」)は、実験で成り立たなかった。

**小さな問い**: `src/` だけの変更で、テストが検出しない挙動が変わりうることを、**非保証として受け入れるか**。

| 答え | 帰結 |
|---|---|
| 受け入れる(第8版の現状) | 決定 (2) を維持。§4.5 に非保証として明記済み。リファクタは軽い。協調的なエージェントが、意図せず挙動を変えても検出できない |
| 受け入れない | すべての `src/` の変更に K を求める。リファクタにも open な承認が必要になる。軽量な経路がなくなり、毎回要件が要る |

## 4. 正しいと確認された点(2 系統)
述語 K・D・T・Q への分離で、第4版の F1・F2(途中状態の拒否、実装前のテストで CI が赤)は再発していない。「同時に open は 1 つ」で関連要件の推定は消えた。D(a)(b) を `open` にだけ課す変更で、履歴の要件を閉じる手順は D の上で成立する。`diff-cover` は、現行の CI 構成(`pull_request`、`fetch-depth: 0`、`uv sync`、`coverage.xml`)で技術的に動く(未配線)。書き込み時を通知にしたことは、D2(ローカルは助言)と整合する。
