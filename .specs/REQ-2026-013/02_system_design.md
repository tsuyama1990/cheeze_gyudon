## 2. 方針
人間は、AI より常に良い判断をするとは限らない。だから、「止まって前に進まないリスク」と「誤るリスク」を天秤にかけて、上げるかどうかを決める [原典: 利用者の発言 2026-10-29]。
1. 人間に作業を頼まない。上げるときは、推奨つきの 1 問にする。
2. 戻せることは進めて、記録する。人間の行為、外に出ること、戻せないことだけを上げる。
3. 迂回になる案は捨てる。分類器に止められたら、再試行しない。

## 3. 判断の表(問いは 2 つ。上から順に当てはめる)
効く原則: 上げる時点をリスクと QCD で決める。硬い制約を回避しない。

| 問い | 当たれば | 時点と上げ方 |
|---|---|---|
| **Q1 迂回か**: ゲート(K/D/T/Q)・分類器・承認の規則を、規則が定めた経路の外で通そうとしているか。例: 承認状態を AI が自分の判断で書き換える、非保証(010 B-14 など)を突く、止められた操作を言い換え・分割・別の道具で再試行する | **捨てる** | 人間に選択肢として示さない。台帳に 1 行(§5) |
| **Q2 人間の行為か、外に出るか、戻せないか**(下の一覧。または「戻す操作を 1 行で書けない」) | **上げる** | その行為が要るときに、AskUserQuestion 1 問(§4)。この判断がなくても進められる作業があれば、それを続ける。同じときに要る問いは 1 回の呼び出しにまとめる。台帳の未確認の行も、ここに相乗りさせる(§5) |
| どちらでもない | **進める** | 上げない。措置(§3.1)を付ける |

Q2 に当たるもの:
- **人間の行為**:
  - 承認、REQ の状態の変更。
  - 結果が変わる変更の main へのマージ(R10)。
  - push。
  - 人間の同意の記録(決定のコミット、「決定: 利用者」の行)の書き換え・並べ替え。
- **品質ゲートを緩めうる・迂回しうる変更**(限定列挙。変更を決める時点で上げる):
  - `scripts/gate.sh`
  - `.github/**`
  - `pyproject.toml` のゲート設定(ruff・mypy・coverage・vulture の閾値や除外)
  - `.pre-commit-config.yaml`
  - 依存パッケージの追加(`uv add` など。`uv.lock` が変わる)
- **Q2 に入れないもの**: `src/jtc_gov/**` と `AGENT.md` の変更そのもの。
  - gov は、これらにも、マージの時点で「人間のマージが必要」を出す [原典: `domain/machinery.py` の `_GLOBS`、`gov check` の出力 [データ 2026-10-29]]。
  - その既存の関所に任せ、実装の判断ごとには止めない。
- **外に出る**: データを外部へ送る・公開する操作。push、`curl` などでの POST、外部サービスへの送信、秘密情報(資格情報)を含む操作。グローバルな設定(`~/.claude/**`)、他のリポジトリの main。
  - **読み取り・検索は含まない**。
- **戻せない**: コミットしていない作業の破棄(`git clean`、`reset --hard`、`checkout -- <path>`)、未マージのローカルブランチの削除(`branch -D`)、`worktree remove --force`。

### 3.1 進めるときの措置(標準メニュー 3 つ)
効く原則: 進めるときも最小のリスク措置を付ける。リアルオプション(先に進めて、後で議論する)。

| 措置 | いつ | コスト |
|---|---|---|
| 1 判断の前にコミットする(戻り先) | 常に | 1 コマンド |
| 2 ブランチ・worktree の中で行う | 常に(既存の規則) | 0 |
| 3 台帳に 1 行(「戻す: <コマンド>。見直し: <何が起きたら>」) | main に入るもの、設計・規則の解釈に関わるもの、設計の範囲を狭めたもの | 1 行 |

- 段階は設けない。判断するのは、措置 3 を付けるかどうかだけ。
- **「戻す」のコマンドに、不可逆な操作(`reset --hard`、`branch -D`、`clean -f`、`push --force` など)を書かない**。戻すときは `git revert`、戻り先のブランチの作成、マージの第 1 親への新しいブランチなど、履歴を残す操作にする。不可逆な操作が要るなら、それは Q2。

### 3.2 push の 1 問
効く原則: 上げ方は最小のコスト。push は利用者の指示があるときだけ。

- ゲートの base は、既定で `origin/main` [原典: `scripts/gate.sh`]。承認や REQ の状態の変更が push されていないと、後続のブランチのゲートが K で詰まる(§1-2)。
- そこで、**承認または REQ の状態の変更を main にマージしたら、同じ時点で push の 1 問を出す**(「push する(推奨)/ まだしない」)。
- 「まだしない」でも、作業は続ける。同じ問いは繰り返さない。
- **例外**: 「まだしない」の後に、base が古い(`origin/main` が遅れている)ことが原因でゲートが止まったときは、**1 回だけ**、止まった理由を付けて、もう一度聞いてよい。
- push は利用者の指示があるときだけ、は変えない。回答が指示になる。

## 4. 承認の流れ(事例 1)
効く原則: 推奨つきの 1 タップ。ファイル編集・ハッシュ計算を人間に頼まない。承認は人間の意思表示。

1. AI が設計をコミットする(コミット X)。
2. AskUserQuestion 1 問: 「REQ-… の設計(コミット X)を承認するか」。選択肢は「承認(推奨)」と「直す点がある(Other)」。
   - **要約差分を必ず付ける**: 前に見せた版(なければ前の REQ)から、何が変わったか。**設計の範囲を狭めた・削った箇所**は、必ず含める。
   - 範囲を狭めたことは、台帳にも 1 行残す。
   - push の 1 問(§3.2)を、同じ呼び出しに入れてよい。
3. 「承認」なら、AI が **X の中身**(`git show X:<path> | sha256sum`)からハッシュを取り、`approval.json` を書く。作業ツリーが X と違えば止める。
4. 決定のコミットのメッセージに、「承認: 利用者の回答 "<回答の引用>"(AskUserQuestion、<日時>)、対象 X」と書く。
5. フックの ASK(011 F05。導入後)は保険。ASK は fail-open なので、例外のときや、フックがない環境では出ない [原典: `global_hook.main`]。
6. **C2 との関係**: C2(`approval.json` を変える PR は人間がマージする)[原典: 010 02 §4.3] に対しては、**手順 2 の「承認」の回答が、その決定のマージの指示も兼ねる**(推奨。確認の回数を増やさないため)。このことを、問いの文面にも書く(「承認すると、決定のコミットを main にマージします」)。
   - 兼ねない形(C2 のマージの確認を別に 1 回出す)も取れる。どちらにするかは DEC-062 で利用者が決める。

**AskUserQuestion は、主の会話で利用者にだけ出す**。サブエージェントや自動化は、承認・決定の質問を出さず、結果を主に返して、主が出す。サブエージェントの回答を、利用者の意思表示として使わない。

これは DEC-033 と C1「エージェントは行わない」を変える**見直しの提案**(DEC-062)。

## 5. 台帳
効く原則: 先に進めて、後で議論できる。人間の確認は 1 問に相乗りさせる。

- **置き場**: 判断が効くリポジトリの、open な REQ の `decisions.md`。
  - open な REQ がなければ、最も新しい REQ に置く。
  - `~/.claude` の判断は、cheeze_gyudon の同じ場所に置く(グローバルなフックの置き場が gov のため [原典: DEC-050])。
  - 新しいファイルは作らない。
- **状態の列に値を 1 つ足す**: `AI`(AI が決め、利用者は未確認)。
- **`AI` を `有効`/`取消` に変えられるのは、利用者の AskUserQuestion の回答があるときだけ**。変更のコミットに、回答を引用する。
- **見直し**: 次に Q2 の問いを出すとき、`AI` の行を 1 行ずつ本文に出し、問いを 1 つ足す(「全部確認(推奨)/ 覆す行を書く(Other)」)。

## 6. 事例 2 の再演(詳細は [worked_example_k_c.md](worked_example_k_c.md))
効く原則: 回避せずに済む流れを設計に含める。

- **根本原因**: 構造・追跡テスト(010-F08)が 010 の設計書だけを読むので、後続の要件はそれを変えるしかない。
- **Q1 で捨てる案**:
  - AI が承認状態を入れ替える。
  - B-14 の非保証を突く。
- **Q2 で上げる案**(どちらも推奨つきの 1 問。同じ重みで併記する):
  - **経路 A**: origin/main(010 がまだ open)の上で保守し、main の未 push の 6 コミットを積み直す。承認ファイルへの書き込み 0 回、push は fast-forward 1 回。人間の決定のコミットの位置が変わるので、同意を取り直す。

- **推奨は経路 A**。人間の操作が少ないため。
- **弱点**: どちらも分類器に止められうる [推論]。止められたら再試行せず、残る操作を 1 問で示す。
