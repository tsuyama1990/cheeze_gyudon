## 1. 目的と範囲

- **目的**: AI エージェントが `main` に入れる変更を、ゲート(設計 → 決定 → 実装)の順序に従わせる。 [決定: D1]
- **保証の境界**: `main` に到達するもの。ローカルの作業ツリーは保証しない。 [決定: D1]
- **MVP の範囲**: §4 の機械的な保証(G)と、人間が守る規約(C)で構成する。前提 A1(資格情報の分離)は未成立で、人間の承認を GitHub の仕組みでは強制しない。 [決定: A1 の許容、承認の扱い(2026-10-27)]
- **範囲外(MVP)**: Phase 5(署名による証明、テレメトリ、ポリシー配布)。 [推論: D13 の推奨。未決]
- **対象リポジトリ**: 公開リポジトリ。保護ルールは、公開か有料プランでのみ作れる(非公開の無料プランでは 403)。 [データ]

## 3. 構成要素

```
 adapters:  cli (click) │ claude_hook (stdin JSON) │ github_action (PR 差分) │ scaffold
                │ 呼ぶ
            checks  (純粋な検査。Findings を返す)
                │ 使う
            derive  (現在ゲート・許可・分類の計算。検査は呼ばない)
                │ 使う
            domain  (型・ID・ゲート列・成果物パターン・分類表)
```

依存の向きは `adapters → checks → derive → domain` の一方向。逆向きの import を禁止する。 [推論: AGENT.md の `adapters → services → domain` に割り当てた]

| 構成要素 | 責務 | 入力 | 副作用 |
|---|---|---|---|
| **domain** | Requirement / Gate / Deliverable / Review / Approval の型。ID 形式(`REQ-YYYY-NNN`、機能タグ `REQ-YYYY-NNN-Fnn`)。ゲート列。成果物パターン。PR 種別とパスの分類表(§6) | — | なし |
| **derive** | 要件ごとの現在ゲート、完了ゲート、`src/` の開閉、PR の種別と関連要件を計算する(§5)。**検査を呼ばない** | `RepoView`(§3.1) | なし |
| **checks** | ペアの存在、トレース、承認マニフェストのハッシュ、PR 種別ごとの通過条件を検査し、Findings を返す | `RepoView`、導出結果 | なし |
| **adapters/cli** | `gov` のコマンド。導出と検査の結果を表示する。雛形と承認マニフェストの雛形を作る | ローカルの git | ファイルを作る |
| **adapters/claude_hook** | PreToolUse の入力(stdin の JSON)から `RepoView` を作り、`checks` を呼び、助言として拒否(exit 2)を返す | stdin、ローカルの git(fetch 済みの `origin/main`) | なし |
| **adapters/github_action** | PR の `base` と `head` から `RepoView` を作り、`checks` を呼び、必須チェックの結果を返す | GitHub のイベント | PR にコメントを書く場合のみ |
| **adapters/scaffold** | `gov init` の出力。テンプレートは 1 か所にあり、このリポジトリ自身の設定も同じ元から出す [推論: D11 は未決。L2 で決める] | — | ファイルを作る |

### 3.1 `RepoView`(純粋性の入力)
`derive` と `checks` は、ファイルシステム、時刻、環境変数、git を直接読まない。adapters が次の値を作って渡す。 [推論: I2 を成立させる形]

| 値 | 型 | 内容 |
|---|---|---|
| `base_files` | `Mapping[str, str]` | `base`(`main`)の全追跡ファイル。パス → 内容 |
| `head_files` | `Mapping[str, str]` | PR の `head` の全追跡ファイル(フックでは、作業ツリーの内容) |
| `changes` | `Sequence[Change]` | 変更の一覧。`Change` は `(旧パス or None, 新パス or None, 状態)`。改名は旧パスと新パスの両方を持つ |

- 依存の循環を作らないため、`derive` の「完了」は存在と承認マニフェストのハッシュ一致だけで決める(検査の合否は含めない)。検査の合否は PR の通過条件として `checks` が別に判定する。 [Opus H2 への対応]
- `Mapping` は読み取り専用の遅延実装でよい(adapters が必要なパスだけを読む)。`derive`/`checks` は `Mapping` の API だけを使うので、I2 は保たれる。全ファイルを事前に読み込む前提ではない。 [DeepSeek N6 への対応]
- フックの `changes` は、`origin/main` と作業ツリー(インデックスを含む)の差分に、これから実行するツール呼び出しの書き込みを反映したもの。CI の `changes` と構成が近くなるが、フックは助言であり、I1 の対象は「同じ `RepoView` を作った場合」に限る。
- 大きなファイル(バイナリなど)の扱いは L2 で決める。

## 4. 不変条件

### 4.1 機械的な保証(G)— CI の必須チェックが判定する

| ID | 性質 |
|---|---|
| G1 | `src/**` を変更する PR は、PR の種別にかかわらず、関連要件の承認マニフェストが `base` で有効かつ open でなければ、必須チェックが失敗する。有効 = 承認済みファイルのハッシュが `base` の現在の内容と一致 |
| G2 | ゲート N の成果物を変更する PR は、(a) `base` でゲート N−1 までが完了していること、(b) `head` でゲート N のペア(設計 + テスト仕様)が揃っていることを満たさなければ失敗する。設計とテスト仕様は同じ PR で作る(AGENT.md の規則) |
| G3 | `main` 上のすべての要件について、仕様の機能タグとテストの `@pytest.mark.requirement` が双方向に一致する。仕様がない要件のタグ、形式が `REQ-YYYY-NNN-Fnn` でないタグも失敗。仕様に機能タグが 1 つもない場合も失敗。要件の marker も設計項目の marker(`design`)も持たないテスト関数も失敗(PR の種別にかかわらず適用) |
| G4 | 品質ゲート(lint、型、デッドコード、重複、カバレッジ)に通らないものは失敗する |
| G5 | PR は §6 の表で分類される。当たったすべての種別の通過条件を、すべて満たさなければ失敗する(§6.4)。分類不能なパスは「その他」に入る |

### 4.2 構造上の性質(I)

| ID | 性質 | 確かめ方 |
|---|---|---|
| I1 | 同じ `RepoView`(`base` の SHA、`changes`、`head_files`)に対して、フックと CI の判定は同じ | 同じ入力を両方の入口に渡して比べる(L1-E13) |
| I2 | `derive`、`checks`、`domain` は、ファイルシステム、時刻、環境変数、git を読まない | 構造検査(import と呼び出しの静的検査。L1-S01) |

### 4.3 人間が守る規約(C)— MVP では GitHub が強制しない

A1 が未成立(エージェントと本人が同一アカウント)のため、次は規約であり、保証ではない。 [決定: 承認の扱い(2026-10-27)]

| ID | 規約 |
|---|---|
| C1 | 承認マニフェストの作成と更新は、人間が行う。エージェントは行わない |
| C2 | 決定 PR と検証機構 PR のマージは、人間が行う |
| C3 | エージェントは、検証機構(§6)を含む PR を、人間の確認なしにマージしない |

A1 が解消された時点で、C1〜C3 を GitHub の仕組み(CODEOWNERS の承認など)で強制する形に引き上げる。引き上げの検証は MVP 後。 [推論]

保証しないこと(N)と前提(A)は `proposal_l1_flow.md` §2 を正とする。A2(`main` の保護)は §8 の構成で満たす。

## 5. データと導出規則

### 5.1 データ

| 概念 | 内容 | 置き場所 | 書く主体 |
|---|---|---|---|
| Requirement | `REQ-YYYY-NNN`、題名 | `.specs/<REQ>/` | エージェント(PR) |
| Deliverable | ゲートごとのペア(設計 + テスト仕様) | `.specs/<REQ>/0N_*`、`tests/` | エージェント(PR) |
| Review | ペルソナの指摘。モデルは 1 つ | `.specs/<REQ>/reviews/` | D7 が決まるまで未定 |
| Approval | **承認マニフェスト**: 要件 ID、状態(`open` / `closed`)、承認した `01〜05` のうち存在する各ファイルの SHA-256、および承認時点の「その要件の marker を持つテスト関数」の SHA-256(関数の粒度は L2 で決める) | `.specs/<REQ>/approval.json`(名前は L2 で決める) | 人間(規約 C1) |

- 現在ゲート、status は保存しない。導出する。`.specs/state.json` は廃止する。 [決定: D2]
- エスカレーション(巻き戻し)は独立のデータではない。承認済みファイルの変更、またはマニフェストの変更として表す。理由は PR の説明とコミットメッセージに残す。ESC 記録のファイルは作らない。 [推論: Opus の代替案を採用(2026-10-27 承認)]

### 5.2 導出規則(`base` の内容に対して)

| 規則 | 内容 |
|---|---|
| ゲート 1〜3 の完了 | そのゲートのペア(設計 + テスト仕様)のファイルが存在する |
| ゲート 4 の完了 | `04_*` と、仕様の全機能タグを marker に持つテストが存在し、かつ承認マニフェストが存在して、承認したすべてのファイルとテスト関数のハッシュが現在の内容と一致する。`05_*`(決定の根拠)は任意で、あればマニフェストのハッシュ対象 |
| 現在ゲート | 完了していない最小のゲート。1〜4 がすべて完了していれば `GATE5_IMPL` |
| `src/` の開閉 | ゲート 4 が完了し、マニフェストの状態が `open` のときだけ開く。`closed` なら閉じる |
| 完了 | マニフェストの状態が `closed` |
| 承認の失効 | `01〜05` のいずれかが承認後に変わると、ハッシュが一致せず、ゲート 4 が未完了に戻る。`src/` が閉じる |
| 巻き戻し | 上の「失効」、またはマニフェストの更新で起きる。履歴の順序は使わない |

- 承認の失効は、巻き戻しと承認後の仕様変更の両方を、同じ規則で表す。 [Opus C2 への対応]
- 承認したテスト関数の**変更と削除**は承認を失効させる。**追加**は失効させない(同じ要件の marker を持つ新しいテストは、実装の段階で足せる)。AGENT.md の「テストの期待値を弱めない」を機械的に守るため。 [決定: N5(2026-10-27、オーナーが推奨を一任)]
- 実装の段階で `01〜05` を直す必要が出たら、直す PR は §6 の「設計 PR」または「決定 PR」になる。マニフェストを更新してから、`src/` の PR を出す。

## 6. PR の分類

PR の種別は、変更パス(旧パスと新パスの両方)から導出する。ブランチ名やラベルは使わない。 [決定: D2 の提案]
1 つの PR が複数の種別に当たる場合も、PR を拒否しない。**マージの規約は最も制限の強い種別**に従い(制限の強さは上の行ほど強い)、**通過条件は当たったすべての種別の和集合**を適用する(§6.4)。 [決定: 最も制限の強い種別に統一(2026-10-27)。通過条件の合成は、第2版レビュー N1 への対応で明確化]

| 順位 | 種別 | 判定(変更パス)。いずれかに当たる | 通過条件(CI) | マージ(規約) |
|---|---|---|---|---|
| 1 | 検証機構 | `.github/**`、`scripts/**`、`pyproject.toml`、`uv.lock`、`.pre-commit-config.yaml`、`tests/conftest.py`、`src/jtc_gov/{domain,derive,checks}/**`、`src/jtc_gov/adapters/{github_action,claude_hook,scaffold}/**`、`src/jtc_gov/templates/**`、分類表(domain 内) | G4。種別を出力に明示する | 人間(C2、C3) |
| 2 | 決定 | `.specs/<REQ>/approval.json`、`.specs/<REQ>/04_*`、`.specs/<REQ>/05_*`、`.specs/<REQ>/reviews/**`。または、承認が open でない要件の marker を持つテストの変更、または承認済みのテスト関数の変更・削除 | G2、G3、G4 | 人間(C2) |
| 3 | 実装 | `src/**`(上の検証機構を除く)。または、承認が open な要件の marker を持つテストの変更 | G1、G3、G4 | 誰でも(CI 合格後) |
| 4 | 設計(ゲート N、N=1〜3) | `.specs/<REQ>/0N_*` | G2、G3、G4 | 誰でも |
| 5 | その他 | 上のどれにも当たらないパス(`doc/**`、`README.md`、`AGENT.md`、`CLAUDE.md`、`LICENSE`、`.gitignore` など) | G4 | 誰でも |

### 6.4 通過条件の合成
- PR が当たった種別ごとの通過条件(表の「通過条件」列)の和集合を、すべて満たす必要がある。例: `src/foo.py` と `approval.json` を含む PR は、「決定」(G2、G3、G4)と「実装」(G1、G3、G4)に当たるので、G1〜G4 すべてが必要。
- `src/**` を含む PR には、種別にかかわらず G1 が適用される。検証機構に分類される `src/jtc_gov/{domain,derive,checks}/**` も同じ。
- マージの規約(人間が必要か)は、最も制限の強い種別で決まる。 [DeepSeek N1 への対応]

### 6.1 要件との紐づけ
- PR に関連する要件は、次のいずれかから導出する: (a) 変更パスの `.specs/<REQ>/`、(b) 変更したテストファイルの marker の要件 ID。
- 種別が「実装」または「決定」で、関連要件を 1 つも導出できない PR は失敗する(`src/` の変更には、要件のタグを持つテストの変更か、`.specs/<REQ>/` の変更が必要)。 [推論: 要件に紐づかない実装を入れない。緊急修正と依存更新の経路は §10 の未決事項]
- 関連要件が複数ある PR は、すべての要件で通過条件を満たす必要がある。

### 6.2 改名と削除
`changes` は旧パスと新パスの両方を持つ。`src/a.py` を `lib/a.py` に改名すると、旧パスが `src/` に当たるため「実装」になる。 [データ: 改名の実験で、`git diff -M --name-only` は新パスだけを出し、`--no-renames` は両方を出す]

### 6.3 未分類のパス
「その他」は CI の検査(G4)だけで通る。新しい最上位ディレクトリにコードを置くと、分類をすり抜ける。実装コードは `src/` に置く規約とし、`scripts/` と `.github/` は検証機構に入れてある。 [推論: 分類表の見直しは、新しいディレクトリが現れたときに行う]

## 7. フロー

1. 設計 PR(1 → 2 → 3)で、ゲートごとのペアを `main` に入れる。
2. 決定 PR で、`04_*`、テスト、承認マニフェスト(`open`)を入れる。人間がマージする。
3. 実装 PR(複数可)で、`src/` とテストを入れる。CI が G1(マニフェスト有効かつ open)を確認する。
4. 完了時に、人間がマニフェストを `closed` にする PR(決定 PR)を出す。以降、その要件の `src/` 変更は G1 で失敗する。
5. 巻き戻しは、`01〜04` を直す PR(承認が失効する)、再度の決定 PR で承認を更新する、の順。
