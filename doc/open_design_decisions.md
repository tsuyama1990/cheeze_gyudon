# jtc-gov 未決の設計判断

`as_is_inventory.md` で確認した事実に基づく、設計上の決定が必要な事項。
各項目は「論点 / 事実 / 選択肢 / 推奨 / 影響」。推奨は **[推論]**(未検証の判断)であり、決定ではない。
決定するのはあなた。決まった項目は末尾の「決定ログ」に移す。

凡例: **[原典]** コード・資料に記載 / **[データ]** 実測(`as_is_inventory.md` に再現手順) / **[推論]** 未検証

---

## 0. 決める順序

後続の判断が先行の判断に依存する。この順に決める。

```
D1 脅威モデル ─┬─ D2 強制の置き場所 ─┬─ D3 人間のサインオフ
               │                     ├─ D4 fail-open / fail-closed
               │                     └─ D5 シェル経由の書き込み
               └─ D12 製品の範囲
D6 ドメインモデルの統一 ─┬─ D7 レビュー/redteam
                         ├─ D8 gate-check の純粋性
                         └─ D9 要件のライフサイクルと複数要件
D10 テスト構造と設計階層の対応 ─ D11 配布(init)と自リポジトリの設定の単一化 ─ D13 Phase 5
```

D1・D2・D6 が確定するまで、実装に入らない。

D1・D2・D6 の提案: [proposal_l1_flow.md](proposal_l1_flow.md)(提案であり、未決定)。

## D1. 脅威モデル: 何から守るか

- **論点**: このツールが相手にするのは、(a) 規約を忘れる・誤解する協調的な AI エージェントか、(b) 迂回を試みる敵対的なエージェントか。
- **事実**:
  - 現状の実装は (a) 向けの防御しか持たない。Bash 経由の書き込みは判定対象外(`as_is_inventory.md` §5.2)、サインオフは自己発行できる(欠陥 A)。[データ]
  - README は 2026-10-26 まで「zero-trust」「kernel-level tool interception」と書いていた(同日、保証・非保証・前提の記述に置き換えた)。[原典]
- **選択肢**:
  1. (a) 協調的エージェントの事故防止。迂回できる経路は文書化し、保証しない範囲として明記する。
  2. (b) 敵対的エージェントも対象。エージェントを OS 権限・サンドボックスで隔離する前提になり、このツール単体では実現できない。
- **推奨 [推論]**: 1。README の「zero-trust」「kernel-level」の表現は事実と合わないため、置き換え済み(2026-10-26、承認済み)。
- **影響**: D2〜D5、README の主張範囲、テスト(迂回を試みるテストを書くか)。

## D2. 強制の置き場所: ローカルのフックか、リモートか

- **論点**: 「通れないこと」の最終的な保証を、どこに置くか。
- **事実**:
  - 非公開リポジトリは無料プランでは保護ルール(ruleset)を作れない(`jtc-spike` で実測: 403「GitHub Pro にアップグレードするか、公開にしてください」)。リモートに権威を置く設計は、公開リポジトリか有料プランが前提になる。[データ 2026-10-27]
  - リモートの `main` は保護されていない(`branches/main/protection` が 404、rulesets が空)。[データ]
  - `ruleset_main.json` と `CODEOWNERS` はテンプレートのまま、宛先もプレースホルダ。[原典+データ]
  - ローカルの pre-commit は、この clone に未導入。[データ]
  - PreToolUse フックは、Claude Code に読み込まれず、仮に正しい場所・構造に置いても exit 1 では拒否にならない(実測。`as_is_inventory.md` §5.1、欠陥 I)。[データ]
  - `pull_request` イベントの CI は PR 側のチェッカーを実行するため、PR がチェッカーを書き換えて通過できる(実測。`proposal_l1_flow.md` §6 U3a)。必須ワークフロー(ruleset の `workflows`)は個人リポジトリでは使えない(422)。[データ]
- **選択肢**:
  1. ローカルのフックを主とする(即時のフィードバックが得られるが、迂回しやすい)。
  2. リモートの保護(必須ステータスチェック + CODEOWNERS 承認)を主とし、ローカルは補助にする。
  3. 両方を主とする(実装コストが最も大きい)。
- **推奨 [推論]**: 2。ローカルのフックは「早く気づく」ための補助、「通らない」保証はリモートに置く。フックの接続は、実機で一度だけ検証してから設計に取り込む。
- **影響**: D3(サインオフの置き場所)、`init` が出力するもの、CI の役割、このリポジトリ自身の設定(ブランチ保護を有効にするかはあなたの判断)。

## D3. 人間のサインオフ

- **論点**: 「人間が承認した」を、何で、どう証明するか。
- **事実**:
  - サインオフは `05_decision.md` 内の文字列 `HUMAN_SIGN_OFF: APPROVED` の存在確認のみ。[原典]
  - `draft-decision` がその文字列(`by @username`)を含むファイルを生成する。エージェントが生成→`gate-check --gate 4` で通る。[データ]
  - README(PR #5 で追加)の「代行コマンドは存在しない」は誤りで、訂正する。[データ]
- **選択肢**:
  1. ファイル内の文字列(現状。偽造可能)。
  2. 対話確認(TTY)。エージェントが TTY を持つ実行形態では無効。
  3. リモートの承認: `05_decision.md` の変更を含む PR に、CODEOWNERS の承認を必須とする(D2 の 2 と一体)。
  4. 署名付きコミット / タグ。
- **MVP の扱い(2026-10-27)**: 別アイデンティティと権限を絞ったトークンの検証は行わない(下の決定ログ)。このため MVP では、エージェントが人間の承認を作れる状態(前提 A1 未成立)を許容する。MVP でも直すのは、`draft-decision` が署名行を自動で書く点(欠陥 A)。署名行は人間が書く。
- **推奨 [推論]**: 3 を権威とし、ローカルの文字列は参考情報に格下げする。`draft-decision` は署名行を **出力しない**(「署名欄」だけを出し、承認は人間が行う)。
- **影響**: `decision_engine`、`gate_keeper`(GATE4 の検証内容)、D2、既存テスト(署名行の生成を前提にしたもの)。

## D4. fail-open / fail-closed の方針

- **論点**: 状態が不明なとき、許可するか、拒否するか。
- **事実** [原典: `verifier.py`, `cli.py`]:

  | 状況 | 現状 |
  |---|---|
  | `state.json` が存在しない | 許可 |
  | `state.json` が壊れている・形式不正 | 拒否 |
  | 未知のツール名(`Edit` 等以外) | 許可 |
  | 対象ツールだがパスを取得できない(`--input` あり) | 拒否 |
  | 引数が何もない | 許可 |
  | アクティブ要件が `requirements` にない | 拒否 |

  「未初期化なら許可」は、既存テストが前提としている振る舞い。[データ]
- **選択肢**: (1) 現状維持 / (2) 「初期化済みのリポジトリ」を定義し、その場合に限り全て fail-closed / (3) 常に fail-closed。
- **推奨 [推論]**: 2。初期化済みの判定は、たとえば `.specs/` ディレクトリまたはフック設定の存在とする。`state.json` を消して迂回する経路を塞ぐ。
- **影響**: 既存テスト(未初期化時に許可を期待するもの)の期待値が変わる。**テストの弱体化ではなく仕様変更**として、設計書側を先に更新して扱う。

## D5. シェル経由の書き込み(Bash 等)

- **論点**: Bash などで `src/` を書き換える経路をどう扱うか。
- **事実**: 現状は対象外。matcher は `Edit|Write|MultiEdit|NotebookEdit` のみ。[原典]
- **選択肢**:
  1. 対象外と明記し、保証しない(D1 の 1 と整合)。
  2. Bash のコマンドを解析して書き込み先を推定する(網羅は困難。誤検知・すり抜けが残る)。
  3. エージェント基盤の権限設定(deny ルール)で制限する。
  4. リモートのチェック(D2)で最終的に検出する。
- **推奨 [推論]**: 1 + 4。シェルの解析は行わない(網羅できないものを「強制」と呼ぶのは誤解を生む)。
- **影響**: README の主張範囲、`doctor` の診断項目。

## D6. ドメインモデルの統一

- **論点**: 要件・ゲート・レビューの概念を、1 か所で定義する。
- **事実**:
  - レビューのモデルが 2 つ(`GateReview` / `GateReviewDeliverable`)あり、gate_id・requirement_id の型が違う。[データ]
  - ゲートの表記が混在: `GATE1_SPEC`(状態)、`gate_1`(redteam の CLI 例)、`Gate 4.5`(README・CODEOWNERS)、`01〜05` のファイル接頭辞。[原典]
  - 要件 ID の形式は `REQ-YYYY-NNN`(トレーサ・レビューモデル)だが、`REQ-000` `REQ-INIT-001`(テストのタグ)も混在。[データ]
  - `gate_review.schema.json` と Pydantic モデルが並存し、スキーマは未参照。[データ]
- **選択肢**: (1) Pydantic モデルを正とし、JSON スキーマは生成物にする / (2) JSON スキーマを正とする / (3) スキーマを廃止する。ID・ゲート名は 1 つの形式に統一する。
- **推奨 [推論]**: 1。`GateId` を唯一のゲート表現にする。「Gate 4.5」は、`GATE4_DETAIL` の完了条件(サインオフ)として吸収する。
- **影響**: `redteam_engine` `decision_engine` `gate_keeper`、全テストのフィクスチャ。

## D7. redteam(敵対的レビュー)の位置づけ

- **論点**: レビューを誰が・何を根拠に出すのか。いま存在させる必要があるか。
- **事実**:
  - `redteam` は固定文言のモックで、LLM を呼ばない。出力は `gate-check` が読めない(欠陥 B)。[データ]
  - `gate-check` は、`reviews/` が無ければレビューを要求しない(存在しなくても通る)。[原典]
  - ペルソナのテンプレート(`*.md`)は `load_persona` で読まれるが、結果に影響しない。[原典]
- **選択肢**: (1) 設計が固まるまで凍結し、`redteam` を一旦削除する / (2) モックのまま D6 に合わせて出力形式を揃える / (3) 実際の LLM 呼び出しまで実装する。
- **推奨 [推論]**: 1 または 2。実体のない機能を「Layer 2: Adversarial Review」と表現し続けるのは、あなたの「YAGNI」「要件に紐づかないコードを書かない」と衝突する(**見直しの提案**)。
- **影響**: README の Layer 2、`review-status`、`draft-decision`、`decision_engine`。

## D8. `gate-check` の純粋性: 検証と前進の分離

- **論点**: 「検証だけ」と「状態を進める」を同じコマンドにしてよいか。
- **事実**: `gate-check` は検証と同時に `state.json` を書き換える。CI 用には別に `ci-verify` を作り、`trace-check` だけを実行している。[原典]
- **選択肢**: (1) 現状維持 / (2) `verify`(読み取り専用)と `advance`(書き込み)に分ける。
- **推奨 [推論]**: 2。CI から呼べる検証は読み取り専用にする。`ci-verify` の「何を検証するのか」が現状は `trace-check` だけで、ゲートの成果物検証が CI に含まれていない。
- **影響**: コマンド体系(外部仕様の変更)、`ci-verify`、e2e。

## D9. 要件のライフサイクルと複数要件

- **論点**: 1 リポジトリで要件を 1 つずつ進めるのか、複数を並行して持つのか。`status` の遷移をどう定義するか。
- **事実**:
  - `active_requirement_id` は 1 つ。[原典]
  - テストには REQ-2026-002〜004 のタグがあるが、仕様ディレクトリは REQ-2026-001 のみ。[データ]
  - `IN_PROGRESS` を設定するコードがなく、`INIT` と `ROLLBACK` から出る遷移もない。`COMPLETED` 後も `src/*` が開いている。[データ]
- **選択肢**: (1) 単一のアクティブ要件のみ。完了した要件はアーカイブへ。(2) 複数要件を並行でき、ブランチ/PR 単位で切り替える。
- **推奨 [推論]**: 1(この製品の現在の規模に合う)。状態遷移図を設計書に書き、全遷移を網羅するテストを置く。`COMPLETED` では `src/*` を閉じる。
- **影響**: `state.json` のスキーマ、トレーサ(他要件のタグの扱い)、`escalate`。

## D10. テスト構造と設計階層(V 字)の対応

- **論点**: L1(アーキテクチャ)↔ E2E、L2(詳細設計)↔ 結合、L3(クラス設計)↔ 単体、の対応を、ディレクトリと marker で機械的に検査する。
- **事実**:
  - 現状は `tests/` 直下の平置き + `e2e/`(1 件)+ `distortions/`(6 件)。[データ]
  - marker `requirement` は要件 ID を示すだけで、設計階層は示さない。仕様が存在するのは REQ-2026-001 のみ。[データ]
  - 全体の方針(`~/.claude/CLAUDE.md` の Gated Modified Waterfall)は `tests/e2e|integration|unit/` と `--strict-markers` を求める。[原典]
- **推奨 [推論]**: 設計書(D1〜D9 の結果)を L1〜L3 に分けて書いたうえで、テストを再配置し、「設計の項目 ↔ テスト」の追跡表を機械的に検査する。`test_coverage_gap.py`(カバレッジ達成目的のテスト)は、設計に紐づくテストに吸収して廃止を検討する。
- **影響**: 全テストの配置、`pyproject.toml` の marker、ゲート定義。

## D11. 配布(`init`)と自リポジトリの設定の単一化

- **論点**: `gov init` が出力する設定と、このリポジトリが実際に使っている設定を、同じ元から出す。
- **事実**:
  - `init` は pre-commit と CI を文字列リテラルで持つ。このリポジトリの実物とは別物(`no-commit-to-branch`、doc-sync、ローカル ruff 等がない)。[原典]
  - `init` が出す PreToolUse 設定は、このリポジトリの `.agent/settings.json` とも形式が違う。[データ: diff]
  - 使用者が受け取る成果物は何か(CLI だけか、設定一式か)が未定義。
- **推奨 [推論]**: テンプレートを 1 か所に置き、`init` とこのリポジトリの両方が同じテンプレートから生成する。
- **影響**: `initializer.py`、`.agent/`・`.pre-commit-config.yaml`・workflow。

## D13. Phase 5(企業規模の運用展開・テレメトリ・署名による証明)

- **論点**: Phase 5 を着手するか、いつ着手するか。
- **事実**:
  - Phase 5 はリポジトリに記載がない。内容は、Jules 向けの開発プロンプト(2026-10-27 にあなたが貼付)にだけ存在する。対応するブランチ・PR はない。[データ]
  - 内容は 3 つ: (a) `gov attest` / `gov verify-attestation`(ファイルのハッシュと承認を結ぶ in-toto 形式の証明)、(b) `gov metrics` / `gov audit-report`(ゲート遷移の所要時間、指摘数、エスカレーション頻度の記録と出力)、(c) `gov sync`(企業共通のポリシーの配布と、ローカル設定の改ざん検出)。[原典: プロンプト]
  - 仕様書(`doc/jtc_governance_framework.md`)のロードマップは Phase 1〜4 の 4 段階で、Phase 5 はない。仕様書の Phase 2 は「フック・コマンドテンプレート(`.agent/`)」で、実装された Phase 2(red team・decision)とは内容が違う。[データ]
  - プロンプトの完了条件は `verify_all.sh` の 7 段階を前提にしているが、現在は 6 段階(`git add -A` の段階を削除した)。[データ]
- **現状の事実との関係** [推論]:
  - (a) 証明は、ハッシュを計算する側の信頼が前提になる。A1(エージェントの資格情報から承認を作れない)が成立しない間は、エージェントが証明を作り直せる。「フックの迂回や force push がなかったこと」は、コミットの性質ではなく、ブランチ保護の設定(A2)と GitHub の承認記録から分かる事実で、ファイルのハッシュからは確認できない。フックは現在エージェントを止めていない(欠陥 I)。
  - (b) 状態を導出する設計(`proposal_l1_flow.md` §3.2)では、ゲートの所要時間は git の履歴と PR の時刻から計算できる。`telemetry.jsonl` を別に書くと、エージェントが書き換えられる記録が増える。トークン消費の見積もりは、このツールが LLM を呼んでいない(redteam は固定文言)ため、取得元がない。
  - (c) ポリシーの配布は D11(`init` と自リポジトリの設定を同じテンプレートから出す)と同じ問題。ローカルの改ざん検出は N1(ローカルは保証しない)の範囲で、検出するならリモート側の検査になる。
  - プロンプトは「Phase 1〜4 は独立に動く、並行して開発する」という進め方を前提にしている。これは現在の不整合(§6 の欠陥)を作った進め方と同じ。
- **選択肢**: (1) 設計が確定するまで着手しない / (2) 3 つを別々の要件に分け、設計後に個別に判断する / (3) プロンプトのまま Jules に渡す。
- **推奨 [推論]**: 1 を経て 2。「要件に紐づかないコードを書かない」「抽象化は 2 つ目の実例が出てから」の規則に沿うと、いま Phase 5 に紐づく要件が存在しない。着手するなら、D11(配布) → A1/A2 の成立後に証明 → 履歴から導出できるか確認してからテレメトリ、の順。
- **影響**: ロードマップ(README・仕様書)、`verify_all.sh` の段階数を参照する文書。
