# L1 テスト計画(E2E)

状態: **スパイラル 1 のベースライン(正式な承認は未)。** 対になる設計書: [02_system_design.md](02_system_design.md)(L1 ↔ E2E)。経緯は [reviews/](reviews/)、決定は [decisions.md](decisions.md)。
根拠の種類: **[原典]** / **[データ]**(実測) / **[推論]**

## 1. 方針

- **E2E(`L1-Exx`)**: 一時ディレクトリに作った実 git リポジトリ(`base` と `head` のコミット)を入力に、`gov` の入口(CLI、フック、GitHub Action のエントリ)の出力と終了コードを確かめる。内部関数は呼ばない。 [推論]
- **統合テスト(`L1-Ixx`)**: 偽の `Repo` を使って、入口どうしの判定の一致を確かめる。E2E の定義(内部関数を呼ばない)には当たらないので分ける。
- **構造検査(`L1-Sxx`)**: 依存の向き、`Repo` 以外から読まないこと、設計と実装の対応を、ソースの静的検査で確かめる。
- **設定の検査(`L1-Cxx`)**: GitHub 側の設定を読み取って確かめる。
- **手動確認(`L1-Mxx`)**: LLM の挙動に依存するもの。自動のテストにしない。
- テストの追跡は、`design` marker を使わない。このリポジトリ自身のテストは、v2 の要件(例: `REQ-2026-010`)の機能タグ(`REQ-2026-010-Fnn`)を `requirement` marker に付ける。設計書の項目と機能タグの対応は §5 の追跡表で持つ。 [推論]
- ディレクトリは E2E が `tests/e2e/`、統合が `tests/integration/`、構造検査が `tests/unit/`(D10 で確定)。 [原典: オーナーの全体方針]
- 入力の書き方: 「テスト」はテストの変更、「仕様」は `.specs/**` の変更を表す。K の判定はこの有無で変わるので、各シナリオに明記する。
