## 3. 正しいと確認できた点
- 状態を内容から導出する方式は、マージ方式(merge / squash / rebase)に依存しない(最終の tree が同じため。ESC の順序付けを除く)。
- 検証機構の変更を人間の承認で守る方向性は筋が通る(CODEOWNERS は base 側のものが使われるため、PR 内で書き換えて逃げられない。ただし C1 が前提)。
- ブランチ名やラベルを判定に使わない判断は正しい。
- フックの現状評価(場所・構造・exit 1)は、コードと実測の両方で正しい。

## 4. Opus が示した代替案: 内容ハッシュに束縛した承認マニフェスト
- 要件ごとに 1 ファイル(例: `.specs/<REQ>/approval`)を置く。中身は「承認時点の `01〜04` の各ファイルのハッシュ」と「open / closed」。
- ゲート 4 完了 ⇔ ハッシュが `main` の現在の内容と一致する。`src/` を開く ⇔ open かつ一致。
- 効果: 巻き戻しはファイルの変更だけで表せる(ESC 記録が不要。H8)。closed で完了後に `src/` を閉じる(C2a)。承認後の仕様変更を検出できる(C2c)。履歴を使わずに導出できる(C2b)。決定 PR と承認を 1 つのファイルにまとめるため、H3 のデッドロックも解ける。
