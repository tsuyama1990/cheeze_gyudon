# MVP 外の積み残し

MVP で作らないと決めたものの一覧。ここが正本。理由と再開の条件だけを書き、設計の本文は元の場所を参照する。MVP に入れるときは、行を消して設計書に移す。

| ID | 積み残し | MVP で作らない理由 | 再開の条件 | 元の場所 |
|---|---|---|---|---|
| B-01 | `gov approve`(承認ファイルのハッシュ生成コマンド) | 手作業で足りる。エージェントが実行できると、承認は人間の行為という規約(C1)が曖昧になる | 手作業のハッシュ作成が負担になったとき | DEC-033、DEC-029 |
| B-02 | 複数の要件を並行して open にする | 1 から複数への緩和は後からできる。複数から 1 へは戻せない | 並行開発が必要になったとき | 02_system_design.md §4(同時に open な承認は 1 つ)、decisions.md D9 |
| B-03 | 承認後のテストの弱体化(期待値を弱める変更)の機械検出 | 規約(AGENT.md)に残す。検出方法が未設計 | 弱体化が実際に起きたとき | 02_system_design.md §4(テスト本体は承認の対象にしない) |
| B-04 | 資格情報の分離(別アイデンティティ、権限を絞ったトークン)。前提 A1 | 作成できなかった。保証は協調的なエージェントに限る | 協調的でないエージェントを扱うとき | DEC-007 |
| B-05 | `main` の保護(ruleset)。前提 A2 | 非公開リポジトリでは使えない | リポジトリを公開する、または有料プランにしたとき | 01_req_spec.md の A2 |
| B-06 | CI の検査器を PR から変更できなくする(`pull_request_target`、`main` 側の検査器)。前提 A3 | 外部の PR でしか検証できない。人間のマージの規約(C2、C3)で代える | 外部の PR で実測できるとき | 01_req_spec.md の A3、DEC-004 |
| B-07 | レビュー/レッドチーム(`review_models`、`redteam_engine`、`decision_engine`) | MVP の範囲外。凍結または削除 | 再開するとき | decisions.md D7、02_system_design.md §10 |
| B-08 | 配布とテンプレート(scaffold の拡張)、GitHub のコメント整形 | MVP の範囲外。`.claude/settings.json` の雛形出力だけ残す | 他のプロジェクトへ配布するとき | decisions.md D11、02_system_design.md §10 |
| B-09 | 企業規模の運用展開、テレメトリ、署名による証明 | MVP の範囲外 | 利用者が増えたとき | decisions.md D13 |
| B-10 | `read` を `git cat-file --batch` にまとめる最適化 | 速度の要件がない | 実測で問題になったとき | 04_detail_design.md Q-L3-1、DEC-014 |
| B-11 | サブモジュール(gitlink)の扱い | MVP では対象外(`read` は `RepoError`) | サブモジュールを使うとき | 04_detail_design.md §5.1 |
| B-12 | 作業: `jtc-spike` リポジトリの削除 | 削除はオーナーが GitHub の画面で行う | いつでも | (オーナーの作業。他に記録なし) |
| B-13 | `test_functions` が pytest の収集と完全には一致しない形(継承した基底クラス、入れ子クラス、別名、`unittest.TestCase` を継承した `Test` で始まらないクラス)の扱い | 協調的なエージェントが通常は書かない形 | その形のテストが実際に使われたとき | 04_detail_design.md §3.3 |
| B-14 | 承認された要件と無関係な `src/` の変更、テストファイル内のヘルパー関数だけの変更(関数の marker に結びつかない)、承認範囲外の `.specs/<REQ>/` のファイル(`06_*` など)、`test_*.py` 以外の `tests/` の変更の扱い | K は承認の有無と、テスト・仕様の要件の照合までを保証する(非保証 N の範囲) | 実際に問題が起きたとき | decisions.md DEC-042 |
| B-15 | 他のリポジトリへ導入したときの摩擦(matome での試用、2026-10-28): (1) `gov init` のフック設定が `.venv/bin/gov` 前提で、`uv tool install` した `gov` を使えない (2) jtc-gov は Python 3.13 必須で、3.12 のリポジトリの `.venv` に入れられない (3) 既存のテストへの `requirement` marker の付与自体が K.a になるので、`gov check` を有効にする PR を後回しにする手順が要る(設計書 §11 の手順を `gov adopt` のような形で支援できる) (4) 既存リポジトリの `ruff` の `fix = true` が、ゲートの中でファイルを書き換える (5) `src/` の中の `test_*.py` という名前の本番コードが T.c に当たる (6) 仕様の ID とテストの対応を機械検査する `test_traceability` は jtc-gov 自身のテストなので、導入先にはない (7) 検査を実機のフックで守るには、導入先の Claude Code セッションをそのリポジトリで起動する必要がある | 配布(B-08)の具体的な課題。matome では手で回避した | 別リポジトリに本格導入するとき | matome の `.specs/REQ-2026-001`、`scripts/gate.sh`、`.claude/settings.json` |
