# L1 提案: 全体フローから導く D1 / D2 / D6

`open_design_decisions.md` の D1(脅威モデル)・D2(強制の置き場所)・D6(ドメインモデル)を、個別ではなく**全体フローから一括で最適化**した提案。
これは**提案**であり、決定ではない。決定されたら `open_design_decisions.md` の決定ログへ移す。

根拠の種類: **[原典]** / **[データ]**(2026-10-26 実測) / **[推論]**(未検証の判断)

---

## 0. 要約

| | 現状 | 提案 |
|---|---|---|
| D1 保証の境界 | 暗黙。README は「zero-trust」 | **「`main` に到達するもの」だけを保証する。** ローカルの作業ツリーは保証しない(明記) |
| D2 権威の置き場所 | ローカルの `state.json` + フック | **リモート(保護された `main` + 必須 CI + 人間の承認)が権威。** ローカルは同じ検査を早く見せるだけ |
| 状態 | `state.json` を各コマンドが書き換える(エージェントも書ける) | **保存せず導出する。** 現在のゲートは、`main` 上の成果物と承認から計算する |
| D6 モデル | レビューが 2 種、ゲート表記が 4 種、ID 形式が混在 | **Requirement / Gate / Deliverable / Review / Approval の 5 概念に統一。** Pydantic を正とし、JSON スキーマは生成する |

この提案の根は 1 点: **「エージェントはローカルで何でもできる」を前提に置くと、ローカルに権威を置く設計は成立しない。**
ローカルのフックも `state.json` も、エージェントが書き換え・無効化できる。だから権威は、エージェントが触れない場所(保護された `main`、人間だけが持つ承認)に置く。

## 1. 全体フロー(提案)

```
 人間 ─ 要件の依頼
   │
   ▼
 [設計 PR]  .specs/<REQ>/0N_* (設計+テスト仕様のペア)  ← エージェントが作成
   │         CI: ペア存在・形式・トレーサビリティ・先行ゲート完了(mainに導出)
   │         マージ: CI 合格のみ(人間の承認は不要)            ← ゲート 1〜3
   ▼
 [決定 PR]  .specs/<REQ>/04_* + 05_decision.md(署名欄のみ。承認は含まない)
   │         CI: 同上 + 「承認」の存在
   │         マージ: CODEOWNER(人間)の承認が必須             ← ゲート 4 = 唯一の人間ゲート
   ▼
 [実装 PR]  src/ + tests/                                      ← ゲート 5
   │         CI: 決定が main で承認済み / 変更パスが許可内 / トレース / 品質ゲート
   │         マージ: CI 合格(+ 必要なら人間)
   ▼
 main に到達 = 保証が成立する唯一の点

 戻り: [エスカレーション PR] ESC 記録を追加 → 以降の導出で GATE N 以降が未完了に戻る
```

- 人間が介入するのは**決定 PR の 1 回だけ**(README の Tri-Polar 決定と同じ位置)。それ以外は CI が機械的に判定する。 [推論: 人間の注意を最小化する設計]
- PR の種別は、**変更パスから導出する**(`src/` を含めば実装 PR、`.specs/<REQ>/0N_*` なら設計 PR N)。ブランチ名やラベルは使わない(エージェントが付け替えられる)。現在の `action_runner.extract_gate_from_branch` はこの方式ではない。 [原典]
- 設計 PR と実装 PR の混在は拒否する。

## 2. D1 提案: 保証の境界を「`main` への到達」に置く

### 保証すること(G)
| ID | 内容 |
|---|---|
| G1 | `src/` を変更する PR は、アクティブ要件の決定(ゲート 4)が `main` 上で人間に承認されていなければマージできない |
| G2 | 設計成果物はペア(設計+テスト仕様)が揃っていなければ次のゲートに進めない |
| G3 | `main` 上のテストが付ける `@pytest.mark.requirement` と仕様の `REQ-xxx-Fnn` は双方向に一致している |
| G4 | 品質ゲート(lint・型・デッドコード・重複・カバレッジ)に通らないものは `main` に入らない |

### 保証しないこと(N)— 明記する
| ID | 内容 |
|---|---|
| N1 | エージェントがローカルで何を書いたか(未コミット・未 push の作業ツリー)。ローカルのフックは助言であり、強制ではない |
| N2 | シェル経由の書き込み。ただし N1 の延長で、`main` に到達する時点で G1〜G4 により検出される |
| N3 | 人間が承認した内容の妥当性(承認は「人間が見た」ことしか証明しない) |
| N4 | 管理者権限・人間の資格情報を持つ者による迂回 |

### 前提(A)— 満たされていなければ保証は成立しない
| ID | 前提 | 現状 |
|---|---|---|
| A1 | **エージェントの資格情報は、承認・管理権限を持たない。** PR を作る・push する権限はあるが、`main` の保護の変更、自分の PR の承認、保護のバイパスはできない | **未成立。** この環境の GitHub トークンは `tsuyama1990` 本人の OAuth トークン(`repo` スコープ、リポジトリ権限 ADMIN)で、PR #1〜#6 の作者も同一 [データ] |
| A2 | `main` に保護(必須 CI + CODEOWNER 承認)が有効 | **未成立。** `branches/main/protection` が 404、rulesets は空 [データ] |
| A3 | CI で実行されるチェッカーは、PR の変更で書き換えられない | **未成立。** `on: pull_request` はPR側のワークフロー・コードを実行する [原典: gate_pipeline.yml]。PR #8 でチェッカーを書き換えて通過できることを実測した(§6 U3a)。対策は §6 [データ+推論] |

A1 は特に重要。**同一の資格情報では、人間の承認とエージェントの承認を区別できない。** A1 が満たされない限り、D3(サインオフ)をどう設計しても、実質的な保証にならない。

> 現行の README の「zero-trust」「kernel-level interception」は、G/N/A の区分に置き換えるのが妥当(**あなたが書いた表現の見直し提案**)。 [推論]

## 3. D2 提案: 権威はリモート、ローカルは同じ検査の先行表示

### 3.1 役割分担
| 層 | 役割 | 強制力 | 実装の同一性 |
|---|---|---|---|
| ローカル: PreToolUse フック | 編集前に「この変更は PR で落ちる」と知らせる | なし(助言) | リモートと**同じ検査関数**を呼ぶ |
| ローカル: `gov status` / `gov verify` | 現在のゲートと不足を表示(読み取り専用) | なし | 同上 |
| CI: `gate-verification` | 全検査を実行し、結果を必須チェックとして返す | あり(必須チェック) | ベース側のコードで実行 |
| `main` の保護 | 必須チェック + CODEOWNER 承認 + 直接 push 禁止 | あり | GitHub の ruleset |
| 人間 | ゲート 4 の決定 PR を承認 | あり | CODEOWNERS |

ローカルのフックと CI が**同じ関数**を呼ぶので、「ローカルでは通るが CI で落ちる」という乖離が構造的に起きにくい。 [推論]

### 3.2 状態は保存せず導出する
- 現状: `state.json` が真実の保管場所で、`gate-check` `escalate` が書き換える。エージェントも書ける。 [データ]
- 提案: **現在のゲートを、`main` 上のファイルから計算する。** 例:
  - ゲート N 完了 ⇔ `main` 上に、その要件のゲート N のペアが存在し、検査に合格し、(ゲート 4 は)承認記録が存在する
  - 承認記録は、**CODEOWNER の承認を必須とするパス**(例: `.specs/<REQ>/approvals/`)にしか置けない → 承認の正当性は、ファイルの文字列ではなく**GitHub のレビュー記録**が担う
  - エスカレーション: `.specs/<REQ>/escalations/ESC-NNN.json` を追加する PR。以降の導出で、対象ゲート以降が未完了に戻る
- これにより:
  - `state.json` の更新コマンドが不要(`gate-check` の「前進」・`escalate` の状態書き換えが消える。D8 が解消)
  - `status`(INIT / IN_PROGRESS / ROLLBACK / COMPLETED)が導出値になり、「遷移の欠落」(D9)の原因が消える。実際、`IN_PROGRESS` を設定するコードは現在存在しない [データ]
  - `COMPLETED` 後の `src/*` の開放(欠陥 D)は、ゲートを開く根拠が「保存された許可リスト」ではなく「その瞬間の導出」になるため、構造的に起きない
- ローカルの `state.json` は、廃止するか、導出結果のキャッシュ(任意、真実ではない)に格下げする。 [推論: 細部は L2 で決める]

### 3.3 サインオフ(D3)はこの構造から決まる
- 承認 = CODEOWNER による PR 承認(GitHub のレビュー記録)。
- `draft-decision` は署名行を**出力しない**(欠陥 A の解消)。生成するのは Tri-Polar の比較表と、署名欄だけ。
- 前提 A1 が必要。独りで開発する場合の現実的な形は、**エージェントを別の GitHub アイデンティティ(bot アカウント / fine-grained PAT / GitHub App)で動かし、あなたの本人アカウントだけが承認できる**構成。GitHub の仕様上、PR の作者は自分の PR を承認できないので、この分離が自然に働く。 [推論: GitHub の挙動は L2 の前に spike で実測する]

### 3.4 この選択で失うもの
- ローカルだけで完結するワークフロー(オフライン・GitHub なし)では、強制が効かない。GitHub を前提にする。 [トレードオフ]
- CI への依存が増える。CI の設計(A3)を誤ると、保証が空洞化する。
- 導出ロジックの正しさが、全体の正しさになる。導出は純粋関数にして、テストで網羅する。

## 4. D6 提案: ドメインモデルの統一

### 4.1 概念は 5 つ
| 概念 | 内容 | 識別子 |
|---|---|---|
| **Requirement** | 1 つの機能要望 | `REQ-YYYY-NNN`(正規表現を 1 か所で定義) |
| **Gate** | 5 段階の固定列: `GATE1_SPEC` → `GATE2_SYSTEM` → `GATE3_INTEGRATION` → `GATE4_DETAIL` → `GATE5_IMPL` | `GateId`(唯一の表現) |
| **Deliverable** | ゲートごとの必須成果物。ペア(設計 + テスト仕様)の定義はデータ(設定)であり、コードに書かない | ゲート → ファイルパターン |
| **Review** | ペルソナによる指摘。**モデルは 1 つ** | 要件 + ゲート + ペルソナ |
| **Approval** | 人間の承認記録。ゲート 4(決定)に紐づく | 要件 + ゲート |

- 「Gate 4.5」は廃止する。「決定の承認」は GATE4_DETAIL の**完了条件**として扱う。 [原典: README・CODEOWNERS・framework 文書が 4.5 を使用]
- 「status」は保存せず導出する(§3.2)。
- 要件 ID は `REQ-YYYY-NNN` のみ。`REQ-000` `REQ-INIT-001` は廃止し、テストの marker も整理する。

### 4.2 型の正と生成物
- **Pydantic モデルを唯一の正**とする。`gate_review.schema.json` は `model_json_schema()` から**生成**し、手書きしない(現在は手書きで未参照 [データ])。
- Review は現状 `GateReview`(redteam / decision が使用)と `GateReviewDeliverable`(gate_keeper が使用)の 2 種があり、型が合わない [データ]。**1 つに統合**する。

### 4.3 層構造(AGENT.md の宣言に合わせて整理)
```
domain      : 5 概念の型、ID 形式、ゲート列、成果物パターン(純粋。I/O なし)
derive      : リポジトリ内容 → Requirement の現在ゲート・許可パス(純粋関数。ファイルの読み取りは呼び出し側が渡す)
checks      : ペア・トレース・承認・パス許可・レビューの各検査(純粋。入力 → Findings)
adapters    : cli(click)/ claude フック(stdin JSON)/ github action(PR 差分)/ scaffold(テンプレート)
```
- `checks` と `derive` が純粋であれば、ローカルのフックと CI が**同じコード**を呼べる(§3.1)。
- `adapters/` が現在空であることは、この構造の導入で自然に埋まる。 [データ: `adapters/` は空]

### U5 の詳細(Claude Code 2.1.310、`claude -p`、各設定で Write を 1 回実行)
| 設定 | フック呼び出し | 書き込み |

結論 [データ]: 現行の `gov verify-tool` は (1) Claude Code が読む場所(`.claude/settings.json`)に無く、(2) 形式が flat で読み込まれず、(3) 仮に読み込まれても exit 1 では拒否にならない。**現在のフックは、いずれの意味でもエージェントを止めていない。**

### 結果から導く設計への反映
- **A3(PR が書き換えられないチェッカー)**: `pull_request` だけでは満たせない(U3a)。必須ワークフロー(U3c)は個人リポジトリで使えない。取れる手段は次のとおり [推論]:
  1. **検証機構の変更に人間の承認を要求する。** CODEOWNERS で `.github/**`・検査コード・`.specs/**/approvals/` を人間に割り当てる。PR が検査を書き換えても、そのパスの変更は人間が承認しない限りマージされない。
  2. チェッカーを PR の外に置く: ワークフローを `main` に置いて `pull_request_target` で実行する(U3b、`main` に載せてから実測)、または固定バージョンのパッケージとして取得する。
- **A1(資格情報の分離)**: 分類器が「自己承認」「管理者によるレビュー回避」を拒否したことは、この実行環境にはその種の安全装置があることを示す。ただし、これはリポジトリの設計としての保証ではない(実行環境の設定に依存し、他の環境では存在しない)。設計上の前提としては、別アイデンティティの導入が依然として必要。
- **D3(サインオフ)**: U2 が未実測のため、ここでの確定は保留する。別アイデンティティを用意した状態で、承認の効き方を実測する。
- **フックの扱い(D2)**: ローカルのフックは助言と位置づける提案(§3.1)を維持する。ただし、位置づけが助言であっても、**配線が正しくなければ助言も出ない**ので、`.claude/settings.json` の入れ子形式・stdin の JSON・exit 2 を採用して、実際に動くことを E2E で検証する。

| U3b | `main` へワークフローを追加する PR(通常のプロセスで作る) |
