## 1. 目的と範囲

- **MVP の範囲**: G1〜G4(§4)を、協調的なエージェントに対して成立させる。前提 A1(資格情報の分離)は未成立のまま許容する。 [決定: A1 の許容(2026-10-27)] [推論: 範囲の書き方]
- **範囲外(MVP)**: Phase 5(署名による証明、テレメトリ、ポリシー配布)。 [推論: D13 の推奨。未決]
- **未決で、L2 で決めるもの**: D3 のサインオフの具体的な仕組み、D4 の fail-open / fail-closed、D5 のシェル経由の書き込み、D7 の red team、D8 のコマンド体系、D9 のライフサイクル細部、D10 のテスト構造、D11 の配布。§9 に一覧。

## 3. 構成要素

```
 ┌─────────────────────────── adapters(入出力) ───────────────────────────┐
 │ cli (click)   claude_hook (stdin JSON)   github_action (PR 差分)   scaffold │
 └───────────────┬──────────────────────────────────────────────────────┘
                 │ 呼ぶ
        ┌────────▼────────┐        ┌───────────────┐
        │     checks      │◄───────│    derive     │   ← リポジトリ内容(読み取り専用)
        │ (純粋な検査)    │        │ (現在ゲート   │
        └────────┬────────┘        │  と許可パス)  │
                 │ 使う            └───────┬───────┘
        ┌────────▼───────────────────────▼────────┐
        │                  domain                  │  ← 型・ID・ゲート列・成果物パターン
        └──────────────────────────────────────────┘
```

依存の向きは `adapters → checks → derive → domain`。逆向きの import を禁止する。 [推論: AGENT.md の依存方向 `adapters → services → domain` に `checks`・`derive` を割り当てた]

| 構成要素 | 責務 | 副作用 |
|---|---|---|
| **domain** | Requirement / Gate / Deliverable / Review / Approval の型。ID 形式(`REQ-YYYY-NNN`)、ゲート列(`GATE1_SPEC` → … → `GATE5_IMPL`)、ゲートごとの成果物パターン | なし |
| **derive** | リポジトリの内容(ファイル一覧と中身)から、要件ごとの現在ゲート・完了ゲート・許可パスを計算する。保存された状態を読まない | なし(入力は呼び出し側が渡す) |
| **checks** | ペア存在、トレーサビリティ、レビュー、承認、パス許可、PR 種別の整合を検査し、指摘(Findings)を返す | なし |
| **adapters/cli** | `gov` のコマンド。導出と検査の結果を表示する。成果物の雛形やエスカレーション記録を作る | ファイルを作る(雛形、ESC 記録)。ゲートは進めない |
| **adapters/claude_hook** | PreToolUse の入力(stdin の JSON)を受け、`checks` を呼び、助言として拒否(exit 2)を返す | なし |
| **adapters/github_action** | PR の変更パスと `main` の内容を読み、`checks` を呼び、結果を必須チェックとして返す | PR にコメントを書く場合のみ |
| **adapters/scaffold** | `gov init` の出力。テンプレートは 1 か所にあり、このリポジトリ自身の設定も同じ元から出す [推論: D11 は未決。L2 で決める] | ファイルを作る |

- `derive` と `checks` が純粋なので、ローカルのフックと CI が同じコードを呼ぶ。「ローカルで通って CI で落ちる」乖離を設計上なくす。 [決定: D2 の提案に基づく。推論部分は §8]
- ゲートを進める操作は存在しない。ゲートは、成果物が `main` にマージされた結果として導出される。 [決定: D2]

## 4. 不変条件(守るべき性質)

保証 G は D1 の決定。以下は、構成要素が満たすべき性質に書き直したもの。

| ID | 性質 | 担当 |
|---|---|---|
| G1 | `src/` を含む PR は、アクティブ要件のゲート 4 の決定が `main` で承認済みでなければ、CI の必須チェックが失敗する | derive + checks + github_action |
| G2 | ゲート N の成果物は、設計とテスト仕様のペアが揃い、ゲート N−1 までが導出で完了していなければ、検査が失敗する | derive + checks |
| G3 | アクティブ要件の `REQ-xxx-Fnn` について、仕様のタグとテストの `@pytest.mark.requirement` が双方向に一致する。仕様に機能タグが 1 つもない場合も失敗 | checks |
| G4 | 品質ゲート(lint、型、デッドコード、重複、カバレッジ)に通らないものは必須チェックが失敗する | CI(`scripts/verify_all.sh`) |
| I1 | 同じ入力に対して、ローカルのフックと CI の判定は同じになる | derive + checks |
| I2 | `derive` と `checks` は、ファイルシステム、時刻、環境変数を直接読まない | domain / derive / checks |
| I3 | 検証機構(CI の定義、検査コード、承認記録)の変更は、人間の承認なしには `main` に入らない [決定: A3 の対策] | CODEOWNERS(github 設定) |

保証しないこと N、前提 A は `proposal_l1_flow.md` §2 を正とする。MVP では A1 が未成立。A2(`main` の保護)と A3(I3)は、リポジトリの設定を作る作業(L2 以降)で満たす。

## 6. フロー

PR の種別は、変更パスから導出する。ブランチ名やラベルは使わない。 [決定: D2 の提案]

| PR 種別 | 判定(変更パス) | 通過条件 | マージ |
|---|---|---|---|
| 設計 PR(ゲート N) | `.specs/<REQ>/0N_*` のみ(N = 1〜3) | G2、G3 の該当部分、G4 | CI 合格 |
| 決定 PR(ゲート 4) | `.specs/<REQ>/04_*`、`05_*`、`tests/` | G2、承認記録の存在(D3 の仕組みで判定) | CI 合格 + 人間の承認 |
| 実装 PR(ゲート 5) | `src/` を含む | G1、G3、G4 | CI 合格 |
| エスカレーション PR | `.specs/<REQ>/escalations/` を含む | ESC 記録の形式 | CI 合格(以降の導出でゲートが戻る) |
| 検証機構の PR | `.github/**`、検査コード、承認記録 | I3 | CI 合格 + 人間の承認 |
| 混在 PR | 上の複数にまたがる | 拒否 | — |

1 つの要件の流れ: 設計 PR(1→2→3)→ 決定 PR → 実装 PR(複数可)→ 完了。エスカレーションで途中のゲートに戻れる。

## 8. 設計上の判断と根拠

| 判断 | 根拠 |
|---|---|
| 権威をリモートに置く | ローカルのフックは Claude Code に読み込まれず、exit 1 では拒否にならない [データ: proposal §6 U5]。エージェントはローカルで何でも書ける [決定: D1] |
| 状態を保存せず導出する | 保存された状態はエージェントが書ける。現在の `status` には遷移の欠落があり、`COMPLETED` 後に `src/*` が開いたままになる [データ: as_is 欠陥 D、§3.3] |
| `derive` と `checks` を純粋にする | ローカルと CI で同じコードを使い、I1 を成立させる。単体テストで網羅できる [推論] |
| PR 種別を変更パスから導出する | ブランチ名とラベルはエージェントが付け替えられる。現在の `extract_gate_from_branch` はブランチ名に依存している [データ: `action_runner.py`] |
| 人間の関与を決定 PR の 1 回に絞る | 承認の形骸化を避ける [推論] |
| 検証機構の変更に人間の承認を要求する | `pull_request` の CI は PR 側のチェッカーを実行し、書き換えて通過できる [データ: proposal §6 U3a]。必須ワークフローは個人リポジトリで使えない [データ: 422] |

制約 [データ]: 保護ルール(ruleset)は、公開リポジトリか有料プランでのみ作れる。非公開の無料プランでは作れない(403)。MVP の対象リポジトリは公開。
