## 観点 3: R12 の実現可能性（状態ファイルと Stop 検査）

### 指摘 3-1: 状態ファイルの寿命管理（クリーンアップ）の欠落
- **重大度**: 中
- **根拠**:
  - 設計書 v3 §5 R12: `PreToolUse の対象リポジトリ解決が、触ったリポジトリを ~/.claude/state/<session> に追記。Stop はそれを読み、各リポジトリの未コミットの変更にだけ、今までと同じ条件でゲートを走らせる`
  - Claude Code フック仕様: フックイベントには `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `CwdChanged`, `FileChanged` があるが、セッション終了を検知するイベント（`SessionEnd` 等）は存在しない。
- **修正案**:
  `~/.claude/state/<session>` を作成・追記したあと、このファイルをいつ破棄するかのライフサイクルが設計に存在しません。セッション終了時に削除されないためゴミファイルが残り続け、長期間のセッションや `claude --resume` で過去セッションを再開した際に、以前触った古いリポジトリが状態ファイルに残留します。ユーザーが別作業でそのリポジトリに未コミット変更を残していた場合、再開セッションの毎ターン末尾で関係のないリポジトリの `scripts/gate.sh` が走ってブロックされるリスクがあります（推測）。
  状態ファイルを維持するなら、`UserPromptSubmit`（新しいユーザー指示の開始時）に状態ファイルを初期化する仕様を明記するか、状態ファイルによるセッション横断記録自体を見送ること。

### 指摘 3-2: 複数リポジトリ並行作業時における WIP 巻き込みブロック
- **重大度**: 中
- **根拠**:
  - 設計書 v3 §5 R12: `Stop はそれを読み、各リポジトリの未コミットの変更にだけ、今までと同じ条件でゲートを走らせる`
  - [stop_gate.sh L14-22](file:///home/tomo/.claude/hooks/stop_gate.sh#L14-L22): ゲートが失敗すると exit 2 で停止し、MAX_BLOCKS（3回）で `NOT DONE` になる。
- **修正案**:
  同一セッション内でリポジトリ A（例: `cheeze_gyudon`）を編集し、途中でユーザーから「リポジトリ B（例: `matome`）のファイルを修正・確認してほしい」と指示された場合、状態ファイルには A と B の両方が記録されます。
  このときリポジトリ A に作業途中の未コミット変更（まだテストが通らない WIP）が残っていると、エージェントがリポジトリ B の作業を完了して会話ターンを終えようとするたびに、Stop フックが A の `gate.sh` を走らせて失敗（exit 2）します。結果としてリポジトリ B での正常な対話や質問まで道連れでブロックされ、3回で `NOT DONE` となってセッションが停止します（推測）。
  Stop フックで複数リポジトリを横断検査するのは過剰（YAGNI）であり、Stop は現行通り「セッションの cwd のリポジトリ」のみを対象とすること。複数リポジトリの最終的なゲート通過はマージスクリプト（`merge-to-main.sh`）および CI で担保すれば十分です。

### 指摘 3-3: Bash 経由の変更検知漏れと並行ツール呼び出し時の競合
- **重大度**: 低
- **根拠**:
  - 設計書 v3 §5 R12: `PreToolUse の対象リポジトリ解決が、触ったリポジトリを ~/.claude/state/<session> に追記`
  - 設計書 v3 §6: `Bash のコマンド文字列の解析は完全にできない[推論]。bash script.sh、python -c、変数、env git で素通りしうる。`
- **修正案**:
  Edit/Write ツールであれば `tool_input.file_path` から対象リポジトリを特定できますが、Bash ツールで実行されたスクリプトやコマンド（例: 別ディレクトリで出力を生成するスクリプト）による変更は PreToolUse でリポジトリを解決できません。また、エージェントが並行ツール実行（Parallel Tool Execution）を行った場合、複数の PreToolUse プロセスが同一のセッションファイルへ同時に追記することでファイル競合が生じる可能性があります（推測）。状態ファイルを導入する場合は、アトミックな追記・ロック機構の考慮、および Bash 経由の変更に対する既知の限界を明記すること。
