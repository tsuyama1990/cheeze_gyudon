## 1. 目的と範囲

- **目的**: AI エージェントが、人間が承認していない設計のまま `src/` を `main` に入れることを防ぐ。 [決定: D1]
- **保証の境界**: `main` に到達するもの。ローカルの作業ツリーは保証しない。 [決定: D1]
- **前提**: 協調的なエージェントの事故防止。資格情報の分離(A1)は未成立で、人間の承認は GitHub で強制せず規約(§4.3)にする。 [決定: D1、A1 の許容]
- **対象リポジトリ**: 公開リポジトリ。保護ルールは、公開か有料プランでのみ作れる(無料の非公開では 403)。 [データ]
- **MVP に含めないもの**: scaffold、Review / red team、PR コメント、テスト本体のハッシュ固定、エスカレーション記録、ゲート順序の CI 強制、PR の 5 種別、PostToolUse フック、Phase 5、`sandbox/`、PR サイズ上限、速度要件、Windows のパス区切り、自作の重複検出、`doc_sync_guard`。カバレッジの必須は維持する。 [決定: 縮小案と制約の撤廃(2026-10-27)]

## 2. 考え方(3 つに分ける)

第4版までの失敗は、性質の違う 3 つを 1 つの仕組みに混ぜたこと。 [推論: L1_review3 §4]

| 性質 | 内容 | 仕組み |
|---|---|---|
| **品質検査(Q)** | どの PR にも常にかける検査: lint、型、テストの合格、カバレッジ、タグの整合 | CI。ゲートの条件を持たせない |
| **鍵(K)** | 人間が承認した設計がなければ、新しい挙動を入れられない。新しい挙動は、テストまたは仕様の変更を伴う `src/` の変更で表れる | 承認マニフェストのハッシュ。「`src/**` を変え、かつテストまたは仕様も変える」PR にだけ適用 |
| **指針** | ペアを揃える、ゲートの順序、レビューの観点 | テンプレート、規約、フックの通知。CI の必須条件にしない |

ゲートの順序とペアの有無は、承認のとき(決定 PR)に 1 度だけ確認する(§5)。PR ごとには確認しない。設計もテストも、途中の状態を経て作られるので、途中の状態を拒否する構造にしない。

## 3. 構成要素

```
 adapters:  cli (click) │ claude_hook (stdin JSON) │ github_action (PR 差分)
                │ 呼ぶ
            checks  (検査。Findings を返す)
                │ 使う
            derive  (承認の有効判定、現在ゲートの表示用の計算。検査は呼ばない)
                │ 使う
            domain  (型・ID・ゲート列・成果物パターン)
```

依存の向きは `adapters → checks → derive → domain` の一方向。逆向きの import を禁止する。 [推論]

| 構成要素 | 責務 | 副作用 |
|---|---|---|
| **domain** | Requirement / Gate / Deliverable / Approval の型。ID 形式(`REQ-YYYY-NNN`、機能タグ `REQ-YYYY-NNN-Fnn`)。ゲート列。成果物パターン | なし |
| **derive** | 承認が有効か、現在ゲート(表示用)、関連要件を計算する(§5) | `Repo` 経由で読むだけ |
| **checks** | K、D(決定)、Q のうちタグの整合を検査し、Findings を返す | `Repo` 経由で読むだけ |
| **adapters/cli** | `gov` のコマンド。導出と検査の結果を表示する | なし |
| **adapters/claude_hook** | Claude Code のフック(§6)。stdin の JSON を受け、`checks` を呼び、拒否は exit 2、通知は標準出力 | なし |
| **adapters/github_action** | PR の `base` と `head` から `Repo` を作り、`checks` を呼び、必須チェックの結果を返す | なし |

### 3.1 `Repo`(`derive` と `checks` が使う唯一の入口)
`derive` と `checks` は、ファイルシステム、時刻、環境変数、git を直接使わない。次の薄いインターフェースだけを通して読む。 [決定: RepoView を薄いインターフェースに替える(2026-10-27)]

| 操作 | 内容 |
|---|---|
| `read(path, ref)` | `ref` の時点のファイルの内容。なければ None |
| `list(ref)` | `ref` の時点の追跡ファイルのパス一覧 |
| `changes(base, head)` | 変更の一覧。改名は旧パスと新パスの両方を持つ |

- `ref` は `base`(`main`)、`head`(PR の先頭)、`index`(ステージ済みの内容。`git commit` のフック用)、`worktree`(作業ツリー。書き込みごとのフック用)。 [DeepSeek N4 への対応]
- 実装は adapters が持つ(git、作業ツリー、テスト用の偽物)。`derive` と `checks` は実装を知らない。これで、フックと CI が同じ `checks` を呼べ、単体テストは偽物で書ける。
- フックは `base` を `origin/main` とし、必要なら `git fetch` する。ネットワーク禁止の制約は撤廃した。 [決定: 2026-10-27]

## 4. 規則

### 4.1 機械的に判定する規則(CI の必須チェック)

| ID | 適用対象 | 規則 |
|---|---|---|
| **K** | `src/**` を変更し、かつ `tests/**` または `.specs/**` も変更する PR | `base` に、open で有効な承認が**ちょうど 1 つ**ある。0 個、または 2 個以上なら失敗 |
| **D** | `approval.json` を変更する PR(決定 PR) | 状態が `open` のマニフェスト: (a) `head` でゲート 1〜4 の成果物(設計と、対のテスト仕様の**文書**)がそろっている。ゲート 4 の対は文書(例: `04_test_spec.md`)で、実行可能なテスト(`tests/`)ではない (b) ハッシュが `head` の内容と一致する (d) 変更後、`open` の承認が 2 つ以上にならない。状態が `closed` のマニフェスト: (c) 仕様の全機能タグに対応するテストの marker が存在する。(a)(b) は求めない(履歴として閉じる要件を含む) |
| **T** | すべての PR | (a) テスト関数は、形式が `REQ-YYYY-NNN-Fnn` の `requirement` marker を持つ (b) marker の要件の仕様(`.specs/<REQ>/01_req_spec.md`)が存在し、そのタグに含まれる |
| **Q** | すべての PR | lint(ruff)、型(mypy)、デッドコード(vulture)、テストの合格、分岐カバレッジ 90% 以上、**変更行のカバレッジ**(閾値は L2。`diff-cover`、dev 依存に既にある)。`closed` にする決定 PR(D(c))も、この Q を通る |

- **承認が有効** = マニフェストが存在し、状態が `open` で、承認済みファイルのハッシュが `base` の現在の内容と一致する。
- 仕様のタグにテストがない状態(途中)は、`open` の間は許す。そろっているかは、`closed` にする決定 PR のときだけ確認する(D(c))。 [決定: G3 の限定(2026-10-27)]
- 規則どうしの適用条件は上の表のとおりで、種別と順位による合成はない。 [決定: 述語化(2026-10-27)]
- **同時に open な承認は 1 つ**とする。K が適用される PR は、その要件のものとして扱い、関連要件の推定(テストの marker やブランチ名)を使わない。複数の要件を並行して進めたい場合は、MVP 後に設計する(D9)。 [決定: 2026-10-27。根拠: 並行開発が統合の混乱を生んだ。1 から複数への緩和は後から追加でき、複数から 1 へは戻せない]

### 4.2 構造上の性質

| ID | 性質 | 確かめ方 |
|---|---|---|
| I1 | 同じ `Repo`(同じ `base`、`head`、`changes`)に対して、フックと CI の K の判定は同じ | 偽の `Repo` を両方の入口に渡して比べる |
| I2 | `domain`、`derive`、`checks` は、ファイルシステム、時刻、環境変数、git を使わない(`Repo` 以外から読まない) | ソースの静的検査 |

### 4.3 人間が守る規約(C)

A1 が未成立なので、次は規約であり、保証ではない。 [決定: 承認の扱い(2026-10-27)]

| ID | 規約 |
|---|---|
| C1 | `approval.json` の作成と更新は、人間が行う。エージェントは行わない |
| C2 | 次の PR のマージは、人間が行う: `approval.json` を変更する PR、検証機構(§4.4)を変更する PR |
| C3 | エージェントは、上の PR を人間の確認なしにマージしない |

CI は、これらの PR であることを出力に明示する(人間のマージが必要と表示する)。強制はしない。A1 の解消後に、CODEOWNERS による承認の強制へ引き上げる。 [推論]

### 4.4 検証機構(変更に人間のマージが必要なもの)
`.github/**`、`scripts/**`、`pyproject.toml`、`uv.lock`、`.pre-commit-config.yaml`、`.claude/settings.json`、`.claude/hooks/**`、任意の `conftest.py`、`AGENT.md`、`CLAUDE.md`、`src/jtc_gov/{domain,derive,checks}/**`、`src/jtc_gov/adapters/{github_action,claude_hook}/**`。 [決定: フック設定はプロジェクトごと(2026-10-27)。推論: 一覧]

`pull_request` の CI は PR 側のチェッカーを実行するため、PR がチェッカーを書き換えて通過できる [データ: proposal §6 U3a]。この穴は C2・C3 で補う。`main` 側のチェッカーで実行する方式は L2 で実測して決める。

## 5. 承認と導出

### 5.1 承認マニフェスト
`.specs/<REQ>/approval.json`(名前は L2 で決める)。中身は、要件 ID、状態(`open` / `closed`)、承認した `01〜05` のうち存在する各ファイルの SHA-256。書く主体は人間(C1)。 [決定: 承認マニフェストの採用(2026-10-27)]

- テスト本体は承認の対象にしない。AGENT.md の「テストの期待値を弱めない」は規約として残る。承認後のテストの弱体化を機械検出するのは MVP 後。 [決定: N5 の取り消し(2026-10-27)]
- 巻き戻しは、承認済みファイルの変更(ハッシュ不一致で承認が失効する)、またはマニフェストの更新で表す。ESC 記録は作らない。理由は PR の説明とコミットメッセージに残す。
- 完了は、状態を `closed` にする(決定 PR)。以降、その要件の `src/` 変更は K で失敗する。再び開くには、人間が `open` に戻す決定 PR を出す。

### 5.2 保存しない状態
現在ゲート、status は保存しない。`.specs/state.json` は廃止する。現在ゲートは**表示用**に、`base` の内容から「ペアがそろっていない最小のゲート」として計算する。CI の必須条件には使わない。 [決定: D2]

### 5.3 K の適用と、小さな変更
承認が防ぎたいのは、承認されていない**新しい挙動**が入ること。新しい挙動は、テストまたは仕様の変更として必ず表れる。 [決定: 2026-10-27]

| PR の内容 | K | 理由 |
|---|---|---|
| `src/**` と、`tests/**` または `.specs/**` を変える | 適用(open で有効な承認がちょうど 1 つ) | 新しい挙動の可能性がある |
| `src/**` だけを変える(テストも仕様も変えない) | 適用しない。Q は必須 | 既存のテストが全部通り、カバレッジも満たすなら、挙動は変わっていない。リファクタに使える |
| 新しい行を足したが、テストで覆われていない | Q の変更行のカバレッジで失敗 | テストなしで挙動を足す抜け道を塞ぐ |
| バグ修正(回帰テストを足す) | 適用 | テストが変わるので、人間が修正用の要件を open にする |
| `pyproject.toml`、`uv.lock` だけ | 適用しない | `src/**` を含まない。検証機構として人間のマージが必要(§4.4) |

- 前提: 全体の分岐カバレッジが 90% あること。テストで覆われない 10% の挙動が変わる可能性は残る。変更行のカバレッジで、新しく足した行は覆わせる。

## 6. フック(プロジェクトごとの `.claude/settings.json`)

`gov init` が、入れ子形式の設定を出す。フックは `gov hook <イベント>` を呼ぶ。拒否は exit 2 と標準エラー出力のメッセージ。 [データ: proposal §6 U5]

| イベント | やること | 性質 |
|---|---|---|
| `PreToolUse`(Edit / Write / MultiEdit / NotebookEdit) | `src/**` への書き込みで、open で有効な承認がちょうど 1 つでなければ、通知を出す(「テストまたは仕様も変える場合は、先に承認が必要」)。**拒否しない**。書き込みの時点では、リファクタ(K 不要)か新しい挙動(K 必要)かを区別できないため。拒否はコミット時、終了時、CI | 通知 |
| `PreToolUse`(Bash の `git commit*`、`git push*`) | コミットされる状態(`index`)に対して、K、D、T、Q を実行する。K はここで初めて、テストや仕様の変更が伴うかを判定できる。コミットは作業のまとまりなので、途中状態の問題が起きない | 拒否 |
| `Stop` | 全検査を実行する。通らなければ終了させない(exit 2)。連続 3 回失敗したら、終了を許し(exit 0)、通らない理由を報告する | 拒否 |
| `SessionStart`、`UserPromptSubmit` | 要件ごとの状態(現在ゲート、承認の有効/失効、`src/` の開閉)を、エージェントに伝える | 通知 |

- フックは助言であり、強制ではない(N1)。配線の確認は、`claude -p` で実際に拒否されることを E2E で確かめる。 [データ: 現行フックは読み込まれず、exit 1 では拒否にならない]
- 速度の要件はない。 [決定: 2026-10-27]

## 7. フロー

1. 人間が要件を出す。エージェントが `.specs/<REQ>/` に 01〜04(設計と、対のテスト仕様)を作り、PR を出す。途中の PR は Q と T だけで通る。
2. 設計が固まったら、決定 PR で `approval.json`(`open`、ハッシュ付き)を入れる。D を CI が確認し、人間がマージする(C1、C2)。
3. 実装 PR(複数可)で `src/` とテストを入れる。K(承認が有効かつ open)を CI が確認する。
4. 完了時に、人間が状態を `closed` にする決定 PR を出す。D(c)で、仕様の全タグに対応するテストがあることを確認する。
5. 設計を直す必要が出たら、`01〜05` を直す PR を出す(承認が失効する)。決定 PR で承認を更新するまで、K で `src/` の PR は失敗する。

## 11. 移行の順序(ブートストラップ)

検査を導入する PR が、自分の導入する K にかかる問題を避けるため、必須チェックにするのを**最後**にする。

1. `Repo`、`derive`、`checks` を、CI の必須にしないまま実装する(`pull_request` では実行するが、結果は参考)。
2. 現行テストの marker を整理する。**先に、現行のカバレッジへの影響を実測する**(テストを削除するとカバレッジが 90% を割る可能性がある)。削除より、要件 ID とタグの付与を優先する。削除するのは、廃止する機能のコードと一緒に消すテストに限る。テスト 96 本のうち、marker なし 6、形式不正 29(`REQ-2026-002-F0x` が 15、`REQ-INIT-001` が 14)、形式は正しいが仕様なし 24(REQ-2026-003 が 17、REQ-2026-004 が 7)を、T を満たす形に直すか削除する。 [データ: AST で数えた]
3. 現行の `REQ-2026-001`(F01 の `state.json` と F05 の `escalate` は廃止対象)は、状態 `closed` のマニフェストを置いて履歴として残す。`closed` のマニフェストには D(a)(b) を求めないので、02〜04 がなくても置ける(D(c) は、仕様のタグにテストがあることを求める)。 [DeepSeek N1 への対応]v2 は新しい要件(例: `REQ-2026-010`)として、01〜04 と `approval.json`(人間が作成)を用意する。
4. フックを入れる(`.claude/settings.json`)。実機の `claude -p` で拒否を確認する。
5. 保護ルール(§8)を適用し、必須チェックにする。以降、直接 push は禁止になり、PR で進める。
