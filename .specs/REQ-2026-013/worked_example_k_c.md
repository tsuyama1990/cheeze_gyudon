# 2 回目の再演・実行手順: REQ-2026-011 の実装がゲートで止まった件(事例 2)

[02_system_design.md](02_system_design.md) §6 の詳細。プロトコルの正本ではなく、この件の作業手順と検証の記録。根拠の種類: [原典] / [データ 日付] / [推論]。

## 1. 根本原因
- 構造テストと追跡テスト(印は REQ-2026-010-F08)は、010 の設計書だけを読む [原典: `tests/unit/test_structure.py`、`test_traceability.py`]。
- 新しいモジュールを足す要件は、このテスト関数を変えるしかない。
- 同じ件の 2 件目も出ている(012 の dfca457)[データ]。
- 既定の base(`origin/main`)では、最初に当たる壁は承認を push していないこと。出るのは `K.b 010/approval.json` ×2 と `K.c 011`[データ 2026-10-29]。

## 2. 経路 A: origin/main の上で保守してから、main を積み直す(一次経路)
- **考え方**:
  - 権威はリモート [原典: DEC-002]。
  - origin/main では 010 はまだ open [データ]。
  - open な 010 の下での保守は、DEC-043 の規則どおり。
  - できあがる履歴は、DEC-043 の経路(開き直す → 保守 → 閉じる)と同じ構造になる。010 が open の間に保守し、その後で閉じる。
- **手順**:
  1. `origin/main` から枝を切り、構造・追跡テストを「すべての REQ の設計を読み、存在の確認は closed の要件だけ」の形にする(010-F08 の保守)。
     - **完了条件**: 対象の REQ と手動確認の行を、データ(各 REQ の計画ファイルと `approval.json`)から導く。REQ ごとの定数(例: feat/global-guard の `MANUAL = {"REQ-2026-010": …, "REQ-2026-011": …}` [原典])を直書きしない。
     - 直書きすると、新しい REQ のたびに 010-F08 の関数を変えることになり、012 以降で同じ K.c が再発する。
  2. その上に、main の未 push の 6 コミットを、中身を変えずに積み直す。
  3. feat/global-guard をその上に rebase する。構造・追跡テストの衝突は、保守版を採って解く。
  4. **ローカルの main を、新しい履歴に置き換える**:
     1. 先に、退避用の ref を作る(例: `git update-ref refs/backup/main-2026-10-29 main`)。
     2. main 以外のチェックアウトから `git branch -f main <新しい履歴の先端>` を実行する。worktree 上で置き換えてもよい。
     3. push の前に、新しい main で `scripts/gate.sh` を全段走らせる。
     - `merge-to-main.sh` は使えない。あれはブランチを `--no-ff` でマージするだけで、main の履歴を置き換えられない [原典]。
     - `branch -f` は main を動かすが、退避用の ref が古い先端を保つので、`git branch -f main refs/backup/main-2026-10-29` で戻せる。`reset --hard` などの戻せない操作は使わない。
     - 今の branch_guard は `git commit` と編集だけを見る。`branch -f` は止めない [原典: `~/.claude/settings.json` の `if: Bash(git commit*)`]。止められないから行うのではない。手順 4 は、Q2 の 1 問で利用者の同意を得てから行う。
- **検証** [データ 2026-10-29、使い捨てのクローン。リポジトリは変更していない]:
  - 手順 1: `gov check --base origin/main` が 0。構造・追跡テストは 69 通過・1 スキップ(origin/main には closed の要件がないので、計画の実装の確認が空になる)。
  - 手順 2: 各段階の `gov check` が 0。テストは 72 通過。
  - 手順 3: `gov check --base <新しい main>` が 0。テストは 77 通過。
  - 新しい main は origin/main の子孫になる。
  - **未確認**: ゲートの全段(ruff、mypy、diff-cover、pre-commit)は走らせていない。保守のテストは仮の実装(JSON を文字列で照合)だった。本番は `load_approvals` を使う。
- **人間の操作**: AskUserQuestion 1 問「経路 A で積み直し、push する(推奨)/ 経路 B / 待つ」。
  - 承認ファイルへの新しい書き込みは 0 回。
  - push は fast-forward の 1 回。
- **変わること**: 人間の決定のコミット d5074a6(010 を閉じ、011 を開く)の位置とハッシュが変わる。中身とメッセージは変えない。同意の記録の並べ替え(Q2)なので、上の 1 問で同意を取り直す。
- **012 との関係**: 保守には 012 の `approved_only` を取り込まない(未承認の設計の先取りになる)。

## 3. 経路 B: DEC-043 の経路(同じ重みで併記)
- 流れ:
  1. 人間の意思表示で、010 を open に戻し、011 を withdrawn にする。
  2. 保守 PR を入れる。
  3. 010 を閉じ、011 を再承認する。
- 承認ファイルの書き込みは 2 回。base が origin/main なので、遷移ごとに push が要る。
- 利点: 人間の決定のコミットを動かさない。
- 欠点: 書き込みと push の回数が多い。

## 4. 分類器
- どちらの経路も、分類器に止められうる [推論]。経路 A は履歴の積み直し、経路 B は承認状態の書き込みを含む。
- 止められたら、再試行しない。
- 両方止められたら、利用者に 1 問で示す: 止まったこと、試したこと、残る操作 1 つ。011 の実装以外の作業は続ける。
