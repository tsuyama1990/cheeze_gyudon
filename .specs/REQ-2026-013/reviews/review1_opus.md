## 2. 評価

### a. QCD か、手続きが増えただけか — Major

### c. 循環・行き詰まり — Blocker(§11 事例 2)
- 案 c が分類器に止められたときの代わりとして「d(F01)を待つ」を挙げているが、**d には決して届かない**。F01 は 013 の承認が要り、013 を open にするには 011 を閉じるか取り下げる必要がある。011 は K.c で閉じられない。取り下げは、分類器に止められたのと同じ種類の書き込み。設計は弱点を「報告に記載」としているが、実際には行き詰まる。
- **K.c の前に push の壁がある**(主張 11)。どの経路でも、最初の一歩は「main を push する(推奨)」の 1 問。
- **gov の規則に従う、より安い別経路** [データ: 使い捨てクローンで検証]: DEC-002 では権威はリモートで、origin/main では 010 はまだ open。origin/main から枝を切り、構造・追跡テストを「すべての REQ を読む」形に保守すると、`gov check --base origin/main` は 0 で通る。その上に main の 6 コミットを積み直すと 0、feat/global-guard を載せても 0 で通る。承認ファイルへの新しい書き込みは 0 回、push は fast-forward の 1 回で済む。代わりに、まだ push していないローカルの main の履歴を組み直すことになり、人間の決定のコミット(010 を閉じる)が保守の後ろに移る。そのため利用者の 1 タップ(「この順に積み直す(推奨)」)が要る。分類器が通すかは [推論]。
- 案 c(DEC-043 の経路)は gov としては通る(主張 21)。分類器が通すかは確認できない。ただし DEC-051 自体に「利用者が明示的に指示して代行させる経路を残す」とあり、明示的な指示のもとで AI が書くことは、既に利用者が想定している。
- **F01 は、言明されていないゲートの弱化を含む**。開き直す経路では、閉じるときに D(c)(仕様のタグごとにテストがある)がもう一度走る。引き継ぎの経路ではこれが走らないので、閉じた要件のテスト関数を消す・印を付け替えることが、検査なしで通る。N2 は理由の検査をしないとは書いているが、カバレッジを失うことは書いていない。
- F01 自身のブランチも K.c に当たる。追跡テストは 010 の計画の ID しか知らないので、L1-E60 などを参照するテストは「stale」として落ちる。直すには 010-F08 の関数を変えるしかない。保守 PR を先に入れる順序が前提になっているのに、それが明記されていない。

### d. 「1 タップの承認 + AI がハッシュを計算して書く」— Major
- 硬い制約の「意思表示は人間」とは両立しうる。DEC-051 が想定する経路でもある。ただし次の 3 つの穴を塞ぐ必要がある。
  1. **フックの fail-open**: 例外で許可になる(主張 19)。フックがない環境(agy、未導入の機械)では ASK が出ない。その結果、AI が自分で承認したことが何の痕跡も残さずに通る。
  2. **人間が読んだ版との結びつきがない**: D(b) はハッシュとファイルの一致しか見ない。要約を見せた後で AI が設計を直してからハッシュを取っても、通る。
  3. **同意の証拠が会話の記録にしか残らない**: `Approval` は `extra="forbid"` なので、ファイルに証拠の欄を足せない。
- 歯止めの案: (i) 意思表示は AskUserQuestion にする。人間の画面に出て記録に残り、分類器も文脈として読む [推論]。フックの ASK は保険として残す。(ii) 承認する版を M1 のコミットのハッシュで示し、決定のコミットのメッセージに「承認: 利用者の回答(引用)、対象 <commit>」を書く。(iii) ASK の文面「approval.json は人間が作ります」(011 の実装)を新しい規則に合わせて直す。人間の操作は 2 回になるが、承認は REQ ごとに 2〜3 回しかなく、費用は小さい。
- 010 B-01 が外した理由(C1 が曖昧になる)への答えとして、上の (ii) を書くべき。

### e. 見落とした失敗と、測れない指標 — Major
- **push を後回しにすることと、ゲートの base が `origin/main` であることは両立しない**。push を遅らせるほど、K.b・K.c と diff-cover の範囲が膨らむ。今日の詰まりの一因がまさにこれ。N3 と「push 前に一括」の方針に、「承認の遷移ごとに push が要る」と書くべき。
- 台帳は open な REQ の decisions.md に置くが、REQ がないときや、REQ の外(グローバル設定、matome)の判断の置き場がない。
- §9 の「覆された率」は、AI が書いて AI が状態を変える台帳から計算するので、自己申告になる。「ASK の停止時間」と「文章で聞いた回数」は測れないと自分で書いている。残るのは AskUserQuestion の回数と停止時間(tool_use と tool_result の時刻の差)だけで、どちらも導入前の値が「2 回」しかなく、効果の比較にならない。
- F02 は PreToolUse の時点で `main...<branch>` を判定する。その後、rebase で中身が変わりうる(協調的なエージェントの前提なら Minor)。

## 3. 直すべき点(優先順、最大 10)
1. 02 §11 事例 2: 「d を待つ」を削除する。最初の一歩を「main を push する(推奨)」にし、§2c の「origin/main の上に積み直す」経路と案 c を並べ、それぞれの必要な操作の回数と、分類器に通るかが [推論] であることを書く。どちらも止められたら、利用者の操作が 1 回要ることを正直に書く。
2. 01 §2・§4、02 §12: F01 と F02 を MVP から外し、backlog に移す。取り込む条件は、F01 は「保守 PR の後に、閉じた要件のテストの変更が 2 件目」、F02 は「利用者がマージの ASK を負担と言ったとき」。
3. (F01 を残す場合)01 §4 F01、04 §3: 引き継いだ閉じた要件について、D(c) と同じ「仕様のタグごとにテストがあるか」の検査を K で行う。N2 に「カバレッジの喪失」を書く。
4. 02 §7.2、DEC-062: 意思表示は AskUserQuestion、ASK は保険にする。承認の対象のコミットと、利用者の回答を決定コミットのメッセージに残す。fail-open と agy では ASK が出ないことを N に書く。
5. 02 §3.1・§3.4: グローバル設定(フック、権限)を L2 以上と定義する。結果が変わる変更の main へのマージは、後続が積み上がるので L2 にする(R10 の見直しの提案を取り下げるか、根拠を測ってから出す)。
6. 02 §3.4、§6: 「人間の同意の記録(決定のコミット、「決定: 利用者」の行)の書き換え」を H=承認とする。台帳の行を「確認済み」にできるのは、AskUserQuestion の回答があるときだけと書く。
7. 02 §3.3・01 N3: 「承認・REQ の状態の遷移ごとに push が要る(base が origin/main のため)」を明記する。push の行で AskUserQuestion と ASK を重ねない。合流点 (b) の循環を解く。
8. 02 §3〜§6: L/H/段階/M を 1 つの表に畳む。「戻せる→進めて記録(戻す:/見直し:)」「人間の行為・外部・グローバル→今すぐ 1 問」「迂回→捨てる」の 3 行にし、M5 と「拮抗」は削除する。

## 4. 判定
**修正(大きめの削減)**。原則(人間に作業を頼まない、推奨つきの 1 問、分類器を信号として扱う、戻せないことだけを上げる)は正しい。動機の 3 件にもよく効く。しかし設計は、同じ効果を数行で得られるところに 30 近い概念を重ねており、QCD のうち C と D を自分で悪化させている。さらに、事例 2 の代わりの道(d を待つ)は行き詰まりで、実際の最初の壁(push していない承認)を取り違えている。F01 は D(c) の再検査を失う、言明されていないゲートの弱化を含む。F02 は実測のないまま、同じ日の利用者の決定(DEC-051)を覆している。直す方向は 3 つ。
- 文章の規則を 3 行の表と、承認の歩み(AskUserQuestion+コミットに結びついた同意の記録+ASK の保険)に絞る。
- F01 と F02 は backlog に移す。
- 今の詰まりは「push(1 問)→ 保守 PR(案 c か、積み直し)」として、操作の回数と分類器のリスクを正直に書く。

ここまで直せば、作り直しは要らない。
