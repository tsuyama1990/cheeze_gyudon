## 観点 3: 実現可能性

### 指摘 3-1: R12（Stop フックの先行ブランチ検査と状態ファイル連携）の破綻
- **重大度**: 高
- **根拠**:
  - 設計書 v2 §5 R12: `PreToolUse の対象リポジトリ解決が、触ったリポジトリを ~/.claude/state/<session> に追記。Stop はそれを読み、各リポジトリで「未コミットの変更または main より先行」ならゲートを走らせる`
  - 現行の [stop_gate.sh L11-13](file:///home/tomo/.claude/hooks/stop_gate.sh#L11-L13): `changed=$(git -C "$root" status --porcelain ...); [ -z "$changed" ] && exit 0;`（未コミットの変更がある場合のみ実行）。
  - 現行の [settings.json L72](file:///home/tomo/.claude/settings.json#L72): Stop フックのタイムアウトは 300 秒。
- **修正案**:
  この仕組みには以下の致命的な運用破綻がある：
  1. **TDD / 対話の全面破壊**: エージェントが作業ブランチで最初のコミット（例: 失敗するテストのコミット）を行った瞬間、そのブランチは恒久的に「main より先行」になる。この状態でエージェントが発言を区切ったりユーザーに確認を求めたりしてターンを終えようとすると、Stop フックが毎回 `gate.sh` を強制実行する。テストが失敗している間は Stop が exit 2 でブロックし続け、3 回で `NOT DONE` となってセッションが強制停止する。
  2. **累積的な遅延とタイムアウト**: セッション中に複数リポジトリ（cheeze_gyudon と matome など）を操作した場合、毎回の会話ターン終了時に両リポジトリのフルゲート（ruff, mypy, vulture, pytest, diff-cover, gov check, pre-commit）が直列に走り、会話ごとに数十秒〜数分の停止時間が発生する。
  3. **状態の残留**: 作業ブランチがマージ・削除されるまで「main より先行」状態が解消されないため、一度コミットした後は、単に「コードの質問をする」だけのターンであってもゲート全通過を強要される。
  したがって、「Stop フックで main より先行するブランチを検査する」設計は完全に撤回すべきである。Stop フックは現行通り「未コミットの変更がある場合」に限定し、main 先行ブランチのゲート通過保証はマージスクリプト（`merge-to-main.sh`）および CI で担保すること。

### 指摘 3-2: R13（コミット履歴順序検査）の誤検知と `jtc_gov` アーキテクチャ不整合
- **重大度**: 高
- **根拠**:
  - 設計書 v2 §5 R13: `ブランチが src/ とテストの両方を変える場合に限り、src/ を変えた最初のコミットが、テストを変えた最初のコミットより前なら失敗(同じコミットは可)`
  - 設計書 [02_system_design.md §3.1](file:///home/tomo/project/cheeze_gyudon/.specs/REQ-2026-010/02_system_design.md#L74-L86): `Repo` インターフェースは `read`, `list`, `changes(base, head)` のみを持つ。コミットログやコミットごとの差分を取得するインターフェースは存在せず、`checks` から直接 `git` を呼ぶことはアーキテクチャ原則（I2）で禁止されている。
- **誤検知の具体例**:
  1. **先行リファクタリングの誤ブロック**: 「既存の `src/utils.py` をリファクタリング（コミット 1）」→「新機能のテストを追加（コミット 2）」→「新機能を実装（コミット 3）」という標準的で推奨される開発順序を踏んだ場合、`src/` を変えた最初のコミット（コミット 1）がテストを変えた最初のコミット（コミット 2）より前になるため、不当に拒否される。
  2. **rebase / autosquash による順序変化**: 作業ブランチを `main` の最新に rebase したり、コミットを整理した際に、コミット日時やトポロジカルソートの順序によって誤ブロックされる。
  3. **マージコミットを含む履歴**: `main` の最新を作業ブランチに `git merge main` で取り込んだ場合、`main` 側のコミットが `base..head` の履歴に混入し、`main` 側の `src/` コミットが「最初の `src/` 変更」とみなされて誤ブロックされる。
  4. **すり抜けの容易性（同一コミットの許可）**: 「同じコミットは可」と定義されているため、エージェントが「実装コードを先に書き、後からテストを書いて、まとめて 1 コミットにする」または「複数コミットを 1 コミットに squash する」だけで検査を完全に素通りできる。
  5. **テストだけ/src だけのブランチの分割すり抜け**: 「両方を変える場合に限り」と限定したため、ブランチ A で `src/` のみをコミットしてマージ（DEC-020 の軽量経路）、ブランチ B でテストのみをコミット、と分割することで容易に迂回できる。
- **修正案**:
  `jtc_gov` の `Repo` インターフェース拡張と Git 履歴パーサの実装コストに見合わず、かつ誤検知とすり抜けの穴が極めて大きい。コミット順序の機械検査は断念し、現行の K 規則（有効な承認マニフェストと仕様・テストの対応関係チェック）および CI での検証に委ねること。

### 指摘 3-3: R06（`git merge` 直接呼出の拒否）のコマンド判定ロジック不備
- **重大度**: 中
- **根拠**:
  - 設計書 v2 §5 R06: `git merge で main を対象にする直接の呼び出しを deny し、スクリプトを案内`
  - Git の `merge` コマンド仕様:
    - カレントブランチが `main` のときに実行するマージコマンドは `git merge <feature-branch>` であり、コマンドライン引数に `main` という文字列は一切現れない。
    - 逆に、作業ブランチ上で最新の main を取り込もうと実行するコマンドは `git merge main` であり、コマンドラインに `main` が現れる。
- **修正案**:
  「コマンドライン文字列に `git merge` と `main` を含むか」という単純なパターンマッチで実装すると、「main 上での作業ブランチのマージ（阻止すべき対象）」が素通りし、「作業ブランチ上での main の取り込み（許可すべき操作）」が誤ブロックされる。
  実装仕様として、「PreToolUse で `git merge` を検知した際、対象リポジトリのブランチを解決し、**カレントブランチが main/master である場合**に拒否する」という判定条件を明記すること。なお、`merge-to-main.sh` 経由の内部呼び出しは PreToolUse の直接対象にならないため、この条件で正常にスクリプトのみを許可できる。

### 指摘 4-1: 失敗事象に対する防御の形骸化と不完全性
- **重大度**: 高
- **根拠**:
  - 設計書 v2 §1 L7-11: 4 件の失敗を問題の出発点としている。
  - 上記分析の通り、4 件中 2 件（テスト先行、設計一致）は機械的に防げず、1 件（approval.json）は ASK のため誤承認の余地がある。

### 指摘 5-1: 移行計画（§9）の「1 まとまり = 1 ブランチ」と複数リポジトリ改訂の矛盾
- **重大度**: 中
- **根拠**:
  - 設計書 v2 §9 L99: `## 9. 移行の順序(1 まとまり = 1 ブランチ)`
  - 設計書 v2 §9 L100: `1. 規則の文章: 共通ブロックの雛形を作り... cheeze_gyudon と matome の AGENT.md に反映。~/.claude/CLAUDE.md の該当部分は、この段で削除し、AGENT.md を指す 1 行にする。gov init の置換と、gov doctor の一致検査もこの段。`
- **修正案**:
  Git のブランチはリポジトリごとに独立しているため、`cheeze_gyudon`、`matome`、そしてホームディレクトリ配下の `~/.claude/CLAUDE.md` を「1 つのブランチ」で同時に変更することは技術的に不可能である。
